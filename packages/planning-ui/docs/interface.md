# 规划界面与接口说明

Tasks 的 Plan、Focus 和邮件归类对话框由本包提供（[README](../README.md)）；宿主见 [Tasks](../../../tasks/README.md)，原生验收见[对照表](../../../tasks/docs/planning-parity.md)。文中的标记（`waiting`、`blocked`、`parked`、`onhold`、`quick`、`active` 等）是 Tasks 任务的规划标记（planning flags），不是普通标签；“规划范围”是任务保存的 stage。日期是各项 owner 定稿的日期；2026-10-17 以前的定稿最初做在已退役的 Todoist Plus 扩展里（[历史](../../../docs/history/todoist-plus.md)）。代码路径相对本包。

## Plan 的组成

Plan 顶部保留当前账户周的本周目标，下方有 Review 和 Week 两个视图。第一次打开默认 Review 和 All，工作／生活过滤不改变任务。浏览另一周只影响 Week 的日期队列，不把当前承诺或本周目标伪装成历史快照。

卡片左边的色条是领域（2026-10-19 owner 决定），Plan 和 Focus 只用这一条规则（`areaColor`，`src/planning-outcomes.ts`）：按任务的领域，自己的，否则最近一层父任务的。工作是 `--plus-area-work`（#6387a3，灰蓝），生活是 `--plus-area-personal`（#a98369，赭石），未分类不着色，只是卡片自己的边线色 `--plus-line`。它用在 Review 和 Week 的事项卡（含选中的）、“下一步”托盘的标题条和步骤卡、快速事项、日历里的步骤、Week 的拖动浮层、Focus 的卡片和所属任务条上；元素设 `--area-color`，CSS 一律读 `var(--area-color, var(--plus-area-none))`。Plan 不列出的任务（例如别处刚完成的步骤）不着色。Review 和 Week 的领域过滤里，“工作”“生活”标签前的 8px 圆点就是图例，“全部”“未分类”没有圆点。颜色不单独表达领域：事项卡的可访问名称带领域，快速事项标题按钮的名称是完整标题加领域（`, Work`／`，工作`），下一步属于托盘标题里的事项，日历卡片下一行写着所属事项或领域。工作和生活的色条对 `--plus-bg` 约 3.8:1 和 3.2:1，满足非文字界面的 3:1。

Review／Week、Review 的领域过滤、本周周回顾是否展开及勾选、Week 选中的承诺和“本周承诺”的折叠由宿主保存（Tasks 存在浏览器 localStorage 的 `tasks.plan-view`，只有 ID 和行号，按字段合并写入），离开再回来、浏览器后退和刷新后恢复（2026-10-17 owner 决定）。Plan 挂载时读一次，之后只在用户改动时写入改动的字段，单纯打开不写入。记住的承诺已不在本周承诺里时选第一个，记住的领域不再出现在过滤里时显示全部；读不到时用默认值，存不进时页面照常工作。Week 自己的领域过滤不记住。同一字段在两个标签页里先后改动时以后改的为准。

### 本周目标

2026-10-16 owner 定稿：工作、生活各一行用户自己写的文字（最多 160 个 UTF-16 单位），原地编辑，存在 Tasks 的 D1（`weekly_bets`，按账户周一和领域；2026-10-20 起，之前在 Todofy 的规划库），不写入任何任务，与任何任务、承诺或标签都没有关联。

- 位置不变，在 Review／Week 上方；两列“工作／Work”“生活／Personal”，窄于 650px 时上下排列；只显示当前账户周，Week 翻到别的周不跟着变。
- 已写：目标文字本身就是编辑按钮（14px、600、可换行、纯文本、不识别链接），悬停时 `--plus-hover` 底色和文字光标，没有铅笔图标；按钮名 `编辑工作目标：{text}`／`Edit work goal: {text}`。
- 空：13px 灰字按钮“写下这周的工作目标”／“Write this week's work goal”（生活同理）。
- 空、上周有：下面多一行 12px 灰字“上周：{text}”，单行省略，完整内容在 `title`；悬停或焦点在这一列时旁边出现强调色的“沿用／Keep”，没有悬停的设备上一直显示；按钮名 `沿用上周的工作目标：{text}`。点一下把上周的文字写成本周的，焦点落在保存好的目标上。这是延续目标的唯一入口。
- 编辑中：原地换成同字号、同位置的一行输入框（`maxlength=160`），占位“这周最想推进的一件事”，标签“本周工作目标”，提示“回车保存 · Esc 取消”（输入框的 `aria-describedby`），剩 20 字以内时加“ · 还可输入 {n} 字”。计划页里提示放在这一列标题行的右端，整块高度不变，下面的看板不动；周回顾里仍在输入框下面一行。保存中输入框只读，末端显示 PendingMark“正在更新…”。
- 焦点框画在目标按钮内侧（`outline-offset: −1px`，同输入框），按 Enter、Esc 或“沿用”回到目标时不压到上面的列标题。
- 别处改过（ETAG_MISMATCH）：输入框下一行 `role=alert`“这条目标已在别处改过。再按回车会用你的文字替换它；按 Esc 查看最新内容。”，草稿保留，同时重读一次 GetPlan 显示最新内容；之后只有 Enter 或 Esc 决定。
- 这一周已结束（ACTION_NOT_ALLOWED）：`role=alert`“这一周已经结束，没有保存。”，草稿留着，Enter 不再写入，Esc 关掉；随后后台重读新的一周。
- 保存失败：现有横幅“未确认保存成功，请重试。”，草稿留在输入框里。
- 未配置、断开或维护中：现有 fieldset 停用，横幅不变，目标文字照常可读。

什么时候保存（`src/BetText.tsx`）：

- 在目标上按 Enter 或 Space 打开编辑框，光标放在末尾。
- Enter 保存；输入法组字时的 Enter（`isComposing` 或 keyCode 229）不算，中文输入不会提前保存。文字没改时直接关掉，不写入。
- Tab 或点页面里别的地方：文字改过且不为空就保存，焦点不动。切换窗口、切到别的应用或标签页被隐藏（`document.hasFocus()` 为 false）不保存，草稿保持打开；Plan 被重新挂载时草稿丢弃，也不写入。
- 离开时框是空的不清空，恢复原来的文字；只有在空框里按 Enter 才清空这一周的目标（保留这一行，正文为空，rev 加 1）。
- Esc 取消，恢复原文，焦点回到目标。
- 按 Enter 或点“沿用”之后焦点落在保存好的目标上；因离开而保存时焦点不动。
- Tab 顺序：工作目标 →（沿用）→ 生活目标 →（沿用）。每列标题是 h3，整块的 aria-label 仍是“本周目标”。
- 结果由隐藏的 `role=status` 读出：“已保存工作目标”“已清空工作目标”“已沿用上周的工作目标”（生活同理）。这个区域一直在，只换文字（`src/announce.ts`）；同一句话连着出现两次时先清空、100ms 后再写，第二次也会被读出。
- 其他写入等待确认时，目标和“沿用”只用 `aria-disabled` 标为不可用（目标变暗、“沿用”变灰且仍只在悬停或焦点时出现，点击无效），不用 `disabled`：否则 Tab 刚移到另一行目标上的焦点会被它自己那次保存夺走。

写入是 UpdateWeeklyBet：只写 D1，不写任务，也没有回执；先比较，文字与已存相同就直接返回已存的目标（所以丢失回答后的重发、跨过周日午夜的重放都安全，请求不带 request ID），否则只接受本周和下周，再按 rev（etag）写入一条。返回的 WeeklyBet 直接合并进 `plan.weeklyBets`，不再读取。GetPlan 在同一批 D1 查询里读上周、本周和下周的目标，最多 6 行。

### Review

2026-10-16 owner 定稿，2026-10-17 加入“搁置”，2026-10-18 本周承诺改为单独一行：从左到右是“该开始／Start now”、“等待中／Waiting”、“搁置／Parked”和三个规划列 Quarter、Month、Week（本季度、本月、本周），各自竖排；第四个规划列 Committed（本周承诺）在它们下方单独占满一整行，卡片横向排列，每行的卡片数与上方的列数相同。前两列没有卡片时整列不渲染。“搁置”和规划列一样始终显示，空时写“拖到这里搁置／Drop here to park”，与其他列同样大小：接受投放的列若到拖动开始才出现，会把正在瞄准的列挤开。没有新标签页。宽窗口里上方的三到六列排成一行；内容区窄于约 800px 时每行两列，窄于约 430px 时一列；本周承诺始终另起一行（`src/review-board.css`）。各列用同一种列和事项卡，样式相同。

每个任务只在一列出现，取第一条命中的规则（`src/review-lanes.ts`）：

0. 带 `parked` 标记：搁置，无论它有没有规划范围、在不在等或该不该开始。所以它也不在任何承诺列表里（Week 的总览、工具栏的数量、周回顾），不是 Week 的下一步，也不算“等待中”。
1. 有自己保存的规划范围（本季度、本月、本周、本周承诺）：留在该列。它在等或该开始时，卡片用一句安静的状态说明，见[截止日期](#截止日期)和[等待中](#等待中)。
2. `waiting` 或 `blocked` 标记，或在等另一个尚未完成的任务（[依赖](#依赖)）：等待中。
3. 启动窗口已开或已过截止，且不是进行中：该开始。只因 7 天日期规则（Candidate If）成为 Week 待选的任务也进该开始，不进 Week。
4. 其余按原有日期规则留在 Week。

小步骤不是所属事项那一列的卡片，即使保存了同一个规划范围，它也只是事项卡里的一步；所以在等或该开始的小步骤在“等待中”或“该开始”有自己的卡。投放有落点检查：按预测写入后，卡片必须在目标列里，否则这次投放不写入，卡片回到原处。所以把这样的卡（或搁置的小步骤）拖进所属事项的列不写入：写入后它会回到原列，或只是事项卡里的一步。只有从“该开始”拖入并标为进行中是确认，照常写入：它可以离开看板，只是不能回到“该开始”。拖入别的规划列（在那里成为自己的卡）照常写入。

事项卡固定高度，领域看左边颜色（2026-10-19 owner 决定）：每张事项卡（Review 各列、Week 的承诺总览和拖动浮层）都是 77px 高，上面是最多两行的标题，下面是钉在底部、靠左的一行 12px 文字：步骤及排程数量，或在等、该开始的卡片换成的一句 muted 状态，“搁置”里的卡片换成“N 天未变动”（它在等时仍写在等；搁置的任务从不“该开始”）。这一行从不换行，可以伸到右上角完成勾选框的下方，太窄时以省略号结尾，所以任何宽度下卡片都一样高；标题只有一行时，标题下面留白。Review 六列（1440px 窗口每行 5 列）时步骤数量完整显示；七列都在、每行 6 列时卡片只有约 155px 宽，步骤数量也以省略号结尾。卡片上不再写“工作／生活”：领域由左边色条表示（见[Plan 的组成](#plan-的组成)），可访问名称是“标题, 领域, 优先级”加状态。标题被截断时，鼠标悬停或键盘焦点停在卡片上约 350ms 后，标题下方浮出完整标题（`src/FullTitle.tsx`），卡片不再带 `title`；浮出的全文最宽 320px、最多 6 行，离窗口右缘不足时从标题末端向左展开，不出窗口，页面也不横向滚动。“搁置”按最久未变动排在前，只先显示前 3 张（侧边的列在规划列上方时，一堆搁置的卡不会把规划列挤出屏幕），其余收在一行 12px 强调色的“再显示 N 项／N more”后面，展开后是“收起／Show fewer”，只是这次显示的状态。状态有两段时合成一行，截止日期那一段在前（`10月22日截止 · 12 天未变动`、`已过 2 天 · 等「订场地」`），所以红色的“已过 N 天”不会被截掉；完整的一句仍在可访问名称里，截止日期的完整日期仍是状态的 `title`。拖动时浮起的卡片与原卡同宽同高（dnd-kit 按原卡设定浮层尺寸），也带抓手。优先级保留其原值，用 14px 旗标和原有优先级颜色表示；静止卡片只用细边线，拖动浮层保留阴影。整体目标不再以每张承诺卡的星标呈现。标题点击打开任务详情；整张卡片都能拖动，像任务列表的行一样（见[整行拖动](#整行拖动)），抓手一直显示，留给键盘和读屏。落在同一列的卡片上调整这一列的顺序（见下段），落在同一列的空白处无变化；跨规划列仅调用该任务的规划范围写入。从“该开始”拖入任一规划列就是确认：同一次 UpdateTask 写入该列的规划范围和 `active`。从“等待中”拖入只写规划范围，不去掉 `waiting`／`blocked`，也不加 `active`。拖入“搁置”只发一次 UpdateTask（`planning_flags` 加上 `parked`）：Tasks 同时去掉规划范围和 `active`（从“该开始”拖入也不标为进行中）；从“搁置”拖入规划列的 UpdateTask 写入该列的规划范围并去掉 `parked`；在任务详情（点搁置卡片的标题打开）里给它选一个规划范围后保存，或点“标为进行中”，同样去掉 `parked`，它随之离开“搁置”，只改领域时不动它。“该开始”和“等待中”不接受投放，落在上面的卡片（包括来自“搁置”的）回到原处。拖动都先显示、按序保存，失败时撤回，见[写入与读取](#写入与读取)。卡片不移动整棵子树。

每一列都可拖动或用键盘调整顺序（2026-10-17 owner 决定）。只有落在同一列的卡片上才换位置：被拖的卡占据那张卡的位置（向上或向左移时在它前面，向下或向右移时在它后面），落在列的空白处、标题或缝隙里不变。拖到同列另一张卡上时，那张卡的上方或下方（本周承诺一行里是左侧或右侧）出现任务列表同样的 2px 强调色插入线，标出真正的落点；拖动期间页面不移动任何卡片，落下前看到的顺序就是数据的顺序。拖到别的列（接受投放的规划列或“搁置”）时那一列照旧着色。键盘：抓手上按空格或回车拿起，方向键移到那个方向的下一张卡或下一列（本周承诺一行里左右键在卡片间移动，从上方的列按下键进入它），空格或回车放下，Esc 取消；落下后焦点留在被移动卡片的抓手上。读屏按页面语言读出卡片标题、列名和位置，例如“已拿起：订场地”“移到：本周承诺第 2 项”“已放下：订场地”，从不读出内部 ID。每个抓手（Review 的卡片，Week 的承诺、步骤、快速事项和日历里的步骤）的描述是同一句操作说明“按空格或回车拿起，方向键移动，空格或回车放下，Esc 取消。”，角色说明是“可拖动／draggable”：说明放在看板自己的隐藏元素里，只作描述。切换页面语言时拖动区重新挂载，说明和播报都换成新的语言。

顺序存在 Tasks 的 D1（`plan_board`，一份文档：一个任务只在一列）。每列先按存好的顺序（已不在这一列的 ID 跳过），其余的按这一列原来的顺序排在后面；“该开始”相反，其余的排在前面，新到期的任务是最要紧的消息。原来的顺序：该开始按截止日期和优先级，等待中和搁置按最久未变动，规划列按事项顺序。跨列投放只写规划范围，卡片排在新列已排好的卡片之后（“该开始”是之前），除非新列存好的顺序里还留着它以前的位置。每列最多存 100 个：移到第 100 个之后的投放不保存。该开始和四个规划列同步到 Tasks：被移动卡片在这一列里的同一项目、分区和父任务下的兄弟任务按列中顺序交换原有的位置（`sort_order`），其他任务不动，这一列里只有它自己时任务不变；等待中和搁置的顺序只存在 `plan_board`（它们按“未变动天数”排序，不写任务）。每次投放一次 ReorderTasks，先显示、按序保存，失败时撤回。Week 的承诺总览与“本周承诺”一列同序。

完成勾选框（2026-10-18 owner 决定）：Review 和 Week 承诺总览的事项卡、下一步托盘的步骤、快速事项和日历里的步骤都有 Tasks 同样的圆形勾选框（`src/CompleteTaskButton.tsx`），可访问名称“完成：标题”／`Complete task: …`，在 Tab 顺序中位于卡片之后、“开始”之前。它与 Focus 的完成是同一个操作：一次 Tasks 写入（CompleteTask）完成任务，并在同一批写入里把它标为该日队列中已完成、结算相关的计时；日历里的步骤带它所在的日期，其余带 Focus 的日期（Tasks 的今天）。重试沿用第一次的请求 ID 和日期。写入期间或卡片等待确认时停用；完成后卡片在重新读取后离开，只有日历里的步骤留在它那天，标为已完成（见[Week](#week)）。带 `quick` 的任务总是可以单独排进日期：Quick 隐含“作为步骤安排”，任务详情里这一项在 Quick 时保持勾选、不能取消。

### Week

### 步骤面板

2026-10-19 owner 决定：步骤（`kind=step`）的规划范围和领域跟随所属事项，它唯一的规划信息是用时。所以在 Plan 和 Focus 里打开步骤时，弹出的是只设用时的面板（`src/StepEditor.tsx`），外观与任务详情相同：标题和关闭按钮，“在任务详情中编辑日期、描述和项目。打开任务”一行，所属任务条（领域色），然后一行“预计用时 [15 分钟] [30 分钟] [60 分钟] [90 分钟] [自定义]”。对话框以标题命名。

- 预设是 `aria-pressed` 按钮，等于已存用时的那个按下，都在 `role=group`、名称“预计用时：{标题}”里。自定义框接受 1–1440 的整数分钟，回车或离开时保存；不合法的值不保存，标成 `aria-invalid`，离开时恢复。Esc 先恢复已存的值，再按一次关闭面板。已存值不是预设时显示在框里，没有估时的步骤没有按下的预设。没有“未估时”选项，也没有“超过 2 小时”那句（卡片上的警示色就够了）。
- 规划范围、领域、任务选项、子任务、添加步骤、截止日期、标为进行中和依赖都不在这里，“打开任务”打开 Tasks 的完整任务详情。
- 选择立即显示为按下，这一步的卡片变暗等待，标题旁出现等待标记；宿主写 Tasks 的 `duration_minutes` 并返回保存的时长和任务新的 etag（`{ estimate, etag }`），确认后直接合并，不整表读取，按下的预设不会闪回旧值。等待期间预设只是 `aria-disabled`，不响应点击，焦点留在按下的按钮上；面板只按任务 ID 挂载，保存不会重新挂载它。保存后读屏读出“已保存预计用时：60 分钟”。失败时现有横幅说明“更改未保存，已恢复”，按下的预设回到已存的值。
- 任务（`kind=task`，含快速事项）仍打开完整的任务详情；其中“步骤与时间”添加小步骤的用时同样是 15／30／60／90 分钟，默认 30，没有“未估时”。

### 截止日期

| 5   | 其余（窗口未到）                    | —            | 不出现，只在任务详情说明                       |

`waiting`／`blocked` 标记和尚未满足的[依赖](#依赖)在列的规则中优先：已过截止、带 `waiting` 的任务（`must_start` 包含它）在“等待中”，在等另一个任务、启动窗口已开的任务也在“等待中”，不在“该开始”。

“该开始”按截止日期从早到晚，同一天按优先级。卡片是标题和一句状态（领域在左边色条和可访问名称里）：`还剩 5 天`、`明天截止`、`今天截止` 或 `已过 2 天`（danger）；英文为 `5 days left`、`Deadline tomorrow`、`Deadline today`、`2 days late`。有规划范围的卡在自己的列写同一句。完整日期是状态的 `title`（`截止日期：10月11日周日`）；读屏只补上状态没说的部分：状态已写日期时只加星期（`11月30日截止，周一`），否则加完整日期（`已过 2 天，10月11日周日`）。

确认有两种：把卡片从“该开始”拖入某个规划列（规划范围和 `active` 一次写入，见 [Review](#review)），或用卡片的悬停操作“开始／Start”，只加 `active`。“开始”平时不占位置，标题用满卡片宽度；只在鼠标悬停或键盘焦点（`:focus-visible`）进入该卡时出现在标题第一行的右端，标题在它下面淡入卡片自己的底色。它只用透明度隐藏，不挪动标题和状态，仍在 Tab 顺序（卡片和完成勾选框之后）和可访问树里，可访问名称为“开始：标题”；不能用时（写入期间、拖动未确认）停用并保持隐藏。没有悬停能力的设备一直显示，盖住标题第一行的末端。有规划范围、在启动窗口里的卡也有“开始”。它是先确认的 UpdateTask（`planning_flags` 加 `active`）写入：确认后合并返回的任务，不再整表读取；“该开始”里的卡离开看板（该列空了就整列消失），有规划范围的卡留在原列、状态消失。焦点移到下一张卡的“开始”，没有了就回到该卡或看板第一张卡；看板旁的 `role="status"` 读出“已标为进行中：标题”。事项卡的拖动尚未确认时，它还带着拖动前的 etag，所以“开始”先停用。

已过截止或已到启动窗口的任务本身和它未完成的小步骤都不在本周已读取的 7 天队列里时，Focus 摘要下方有一行安静文字，见[Focus 与计时](#focus-与计时)。Week 的承诺总览用同一张事项卡，但始终显示步骤和排程数量，不写在等或该开始的状态：那里是安排步骤的地方。不把启动窗口里的任务投进 Week 列。

有截止日期但没设提前开始的任务只在周回顾出现一行“N 项截止还没设提前量”；展开后每项可直接用任务详情的同一个提前量下拉框选择，看板和其他地方都不显示。已过截止、又没设提前量的任务按规则 2 也在“该开始”。

### 等待中

“等待中”是 Review 的第二列，紧挨“该开始”右侧，只在有没有自己规划范围、带 `waiting` 或 `blocked` 标记或在等另一个任务的任务时出现（搁置的任务在“搁置”，不在这里，周回顾的计数同样不算它们）；有规划范围的在等任务留在自己的列，卡片写同一句状态。在等另一个任务时，“N 天未变动”换成 `等「订场地」`（多个时 `等 2 项`；英文 `Waiting for “Book venue”`、`Waiting for 2 tasks`），截止日期那一段照旧，见[依赖](#依赖)。卡片按任务的最后修改时间排列，最久未变动的在前，状态为“12 天未变动”（按满 24 小时计，不足一天为“1 天内有变动”；英文 `No change in 12 days`、`Changed within a day`）；有截止日期时前面加截止日期那一段：`10月22日截止 · 12 天未变动`（英文 `Deadline Oct 22 · No change in 12 days`），已过截止是 `已过 2 天 · 12 天未变动`（danger，与“该开始”同一句，看板上只有这一种红字），两段合成一行，截止那一段在前。由此承接原来按截止日期列出等待任务的筛选器。任何编辑都会重置这个时间，所以它不表示已等待多久，也不推断在等谁。

卡片没有悬停操作：点击标题打开任务详情（那里仍可添加步骤、加入今天和打开完整任务），拖入规划列只写规划范围。它不移除标记、不联系任何人，也没有新的存储。

### 依赖

2026-10-16 owner 定稿（设计 plus-next §2，数据层 §5.1）：一个任务可以等其他任务完成。依赖存在 Tasks 的 D1（`task_dependencies`），记在等待的任务上，是两个任务 ID 之间的一条边；不写进任务的标题、描述或标签，也不设 `blocked`。它只影响显示：所等的任务完成后，这个任务显示为可以开始，不改日期、不加减标签。旧标题后缀 `<k:… dep:…>` 在 Plan 里隐藏。

规则（`src/dependencies.ts`，完整读取之后）：

- 所等的任务 B 在活动列表里、Tasks 也没说它已完成就在等；B 不在活动列表里就算满足（“消失即满足”）。B 被删除时，Tasks 删掉等它的依赖；A 完成时，删掉 A 的依赖。B 所在的项目归档时，Tasks 也答 `done`，与 Plan 一致。被重新打开的 B、项目恢复后的 B 又出现在列表里时重新算在等。
- 循环任务完成时只推进日期、ID 不变：任务的 `completed_count` 在每次完成时加一、撤销时减一。建立依赖时 Tasks 记下 B 当时的计数，B 在那之后的下一次完成（计数大于记下的值）就算满足，Tasks 在每个依赖上答 `done`，以后的循环不再挡住 A；要等 B 的再下一次，就在选择框里再选一次 B，从当时的计数重新记起。Tasks 对集合里已有的依赖保持原样，已满足的也不重新开始，所以 Plan 先发不含 B 的集合，再发含 B 的集合（两次 UpdateTask）。
- 只有仍在等的依赖算数：每个任务最多等 5 项，全部最多 300 条；不能等自己，也不能互相等待（含经过其他任务的环）。已满足的依赖不构成环，也不占 5 项：任务已有 5 条（或全部已有 300 条）时，它最早一条已满足的依赖给新的让位。选择时就不让选；Tasks 写入时用一次读取再查一次，并在同一个批次里再核对环和 300 条，两个标签页同时写也不会成环。

**任务详情的“依赖 / Depends on”段**：在 Plan 的任务详情里，位于“截止日期”段之后，标题样式与“下一步”“截止日期”相同。

- 每个尚未满足的依赖一行：13px 标题按钮（在 Plan 中打开它的编辑器），循环任务右侧写 `下一次完成后 / After its next completion`；最右是 24px 的 ×，可访问名称 `移除依赖：订场地`，平时透明度为 0，只在悬停或键盘焦点进入这一行时出现，没有悬停能力的设备一直显示。
- 已满足的不逐条列出：全部满足时写 `所等的任务都已完成，可以开始了 / Everything it waits for is done — ready to start`，部分满足时 `另有 1 项已完成 / 1 more is done`。这一行右端同样有 24px 的 ×（`移除已完成的依赖 / Remove the done dependencies`），只在悬停或键盘焦点时出现，一次排队写入移除这些已满足的依赖，读出 `已移除已完成的依赖`。不移除时，它们在这个任务完成或删除时由 Tasks 删除，或给新依赖让位；循环任务一直在列表里，所以这一行会留到移除或被新依赖替换为止。
- 有任务在等它时多一行只读文字：`「发邀请函」在等它`，多个时 `「发邀请函」等 2 项在等它`。
- `+ 添加依赖 / Add a dependency` 是 `.plus-text-button`；已有 5 项仍在等时停用，`title` 为 `最多 5 项 / Up to 5`。
- 行高 32px（含下边线），带 × 的已保存行和带等待标记的待确认行一样高，确认时不跳动。标题按钮平时像普通文字，悬停或键盘焦点时加下划线，表示点它会打开那个任务。

输入法组字期间，Enter、方向键和 Escape 交由输入法处理，不移动选项或添加依赖。选择框是内联的，不在 Plan 的对话框里再套一层：32px 输入框自动获得焦点，占位文字 `搜索任务或父任务 / Search tasks or parents`；输入后在已完整读取的活动任务中按标题或父任务即时搜索，规则与原“更换目标”相同，没有语法；没有输入时不列出任何任务。结果最多 6 行，每行至少 28px：标题 13px，右侧是父任务路径（12px muted）。不列出任务自己、它的父任务和它的步骤，以及它仍在等的任务；已满足的循环任务会再列出，选它就等它的下一次完成。会形成循环的任务（按仍在等的依赖）仍列出但为灰色，右侧写 `会互相等待 / Would wait on each other`；灰色的行不能选择，也从不高亮：高亮从第一个能选的行开始，↑↓ 只在能选的行之间移动，鼠标移到灰色行上不改变高亮，Enter 添加高亮的那一行；Escape 或 `取消 / Cancel` 收起选择框，Escape 不再传给外面的对话框，焦点回到“添加依赖”。

选中即写入，是先确认的一次 UpdateTask（mask `dependencies`，带 Plan 持有的 etag 发送这个任务的新的依赖集合；再选已满足的循环任务时是先移除再加入的两次）：新行先带现有的等待标记（PendingMark）显示，写入期间停用写入控件，确认后合并返回的这个任务（新的 etag）和它的依赖，不再整表读取；编辑器的 `role="status"` 读出 `已添加依赖：订场地`。点 × 同样是一次写入，读出 `已移除依赖：订场地`。失败时用原有错误区域：Tasks 拒绝时写 `Not added: this dependency cannot be added now. Refresh and try again.`（别的标签页刚改过依赖成环、到了上限或所等的任务已不在待办中都是同一个拒绝，所以不猜原因；和其他 API 错误一样只有英文），任务已不存在时写 `Not added: one of these tasks is no longer active. Refresh and try again.`。

**看板与其他位置**：只因依赖而在等、又没有自己规划范围的任务在“等待中”，排序规则不变（最久未变动的在前）；有自己规划范围的留在原列。卡片计数那一段换成一句安静的状态 `等「订场地」`／`等 2 项`，有截止日期时截止日期那一段在它前面（`已过 2 天 · 等「订场地」`），可访问名称带同一句和完整标题；在等的卡片没有“开始”。所等任务的标题最宽 7em（中文约 7 个字），太长时在引号里以省略号结尾，引号保留，悬停提示完整标题；整句只占一行，卡片窄时以省略号结尾，不会溢出卡片。Focus 的那一行和周回顾的“等待中”计数都包含这类任务；Week 的承诺总览照旧只显示步骤和排程数。

依赖写在等待的任务上，算作改动它：“等待中”的“N 天未变动”从这次写入重新计起（2026-10-20）。

### 周日选择留到下周

在账户时区的周日，在 Plan 里把事项设为本周承诺，Tasks 把它记为下周的承诺（任务的 `committed_week` 是下周一），周一读取时它仍是承诺；再下一个周一按普通承诺处理。只有写规划范围（`stage`）的写入算数。本周更早做出的承诺在下周一读作“本周”（weekly）：重置是读取规则，这个任务下一次写入时才存下。目标是文字，按周保存，从不被重置。

周日清单第 5 行标题是“下周承诺与目标／Next week's commitments and goals”，说明：“在 Plan 中周日选的承诺会留到下周，其余的周一照常重置。目标按周保存，不会被清除。”

- 展开按钮“选要留到下周的承诺（{n}）”只列承诺；周日想保留一个已在本周承诺中的事项，点“留到下周”：它再发送一次同样的承诺写入，规划范围不变，Tasks 只把它记到下周。看板中周日拖入本周承诺，确认后清单立即显示为“已留到下周”，不再提供重复写入；已留下的事项之后在周日被移除承诺，就不再留到下周。
- 下面固定两行（`.weekly-review-items` 的样式）：先是灰色的“工作”“生活”，再是下周目标，编辑方式同上；空时“写下周的工作目标”，输入框标签“下周工作目标”，按钮名“编辑下周工作目标：{text}”。这里不放“沿用本周”：沿用只有一个入口，就是周一起空着的本周目标旁的“上周：… · 沿用”。

任务详情只发送用户改动的字段，周日只改领域不会把承诺误留到下周。后端规则见 [Tasks 的设计](../../../tasks/docs/design.md)和 `tasks/worker/src/planning.ts`。

## Focus 与计时

Focus 显示 Tasks 的今天（`ListFocusDaysResponse.today`，即账户时区的今天）的未完成队列，顺序与 Week 相同。队列、计时和用时记录都在 Tasks 自己的 D1（`proto/tasks/ui/v1/focus.proto`）。Plan 按 Tasks 的今天（`PlanState.today`，GetPlan 的 `today`）排列和计算状态，与 Focus 是同一天。卡片标题在上方，短所属事项、估时和已用时间在下方。空队列只有“调整计划”入口，不出现另一套任务挑选器。

**视图与日期**（2026-10-19 owner 决定）：标题下方是“日／周／月”三个标签（`role="tablist"`，名为“专注视图”，样式同 Plan 的视图标签），右侧是 28px 的前一天／后一天箭头（周是上一周／下一周，月是上个月／下个月），再是“今天”按钮：回到含今天的那一天、那一周或那个月，已在时不可用。窄时箭头一组换到下一行，靠右。没有键盘快捷键。每次进入 Focus 都从今天的“日”开始，视图、日期和“已完成”勾选都不记住：Focus 是用来做事的。页面副标题跟随所显示的范围：日是那一天（“10月13日周二”），周是“第 42 周 · 10月12日起”，月是“2026年10月”，后面是时区；下方不再重复日期。

摘要下方可能有一行安静文字（样式同 Week 的承诺提示，12px muted，悬停时强调色加下划线，没有图标），例如“1 项已过截止、2 项已到启动窗口，这周还没有安排”／“1 past deadline and 2 in their start window, not planned this week”。只有“已过截止”或“已到启动窗口”、又不带 `waiting`／`blocked`、也不在等另一个任务的任务（与看板一致：已过截止的在等任务在“等待中”）本身和它未完成的小步骤都不在本周已读取的 7 天队列里时才出现，每个任务只数一次，有自己规划范围、在原列写明状态的也算，所以数目可能多于“该开始”一列的卡片；Plan 正在看别的周时只看今天的队列；队列为空时也显示。点击打开 Plan › Review（全部领域），焦点放在“该开始”一列上；该列为空时（该开始的任务都有自己的规划范围）放在第一张该开始的卡上。按钮提示“在计划中查看”。它只提示，不往队列里加任何东西。它和番茄钟完成的那一行只在今天出现。

**今天的“日”**：摘要一行分两组，可换行。左边是未完成步骤的估时合计、步骤数、未估时数，再是“· 已用 2h 5m”／“· 2h 5m logged”：当天的记录加上计在这一天的进行中或暂停的计时，大于零时才显示，每秒只更新这一小段（`LoggedTime`，`src/StatusMarks.tsx`），整页不重绘。右边（`margin-left: auto`）是计时方式和“调整计划”，窄时整组换到下一行，仍靠右。计时方式默认“正计时”，排在最前，另有 25 分钟、50 分钟；名称“计时方式”／`Timer duration` 不变。正计时就是 owner 说的“完成一个步骤用了多久”：开始，做事，然后勾选完成；完成的那次 Tasks 写入结束这段计时，并存下它的用时。

每个 Tasks 步骤显示独立的完成控件和计时按钮。完成控件是优先级圆圈（P1 红、P2 橙、P3 蓝带浅色底，P4 灰），与 Review 卡片一致；Plan 没有列出的任务（标题和所属事项来自 Tasks 的读取）没有完成控件，保留同宽空位，标题对齐，它的色条跟随 Plan 列出的父任务，否则不着色。卡片下方一行是“预计 30m · 已用 35m”／`Est. 30m · 35m logged`，没有估时写“未估时”，没有记录时写“记录时间”／`Log time`。“已用”是一个安静的按钮（12px，正文色，悬停加下划线，`aria-haspopup="dialog"`、`aria-expanded`），是卡片上唯一的时间：这张卡的计时进行中或暂停时，它显示已存记录加这一段的时间，如“35:12”，每秒只更新自己，卡片和列表不重绘；否则按整分钟显示。它的可访问名称是“已用 35m （标题）”／`35m logged (title)`。原来另外的经过时间输出已经去掉。Start 带上任务的领域（自己的，否则父任务的；未分类为空），这段计时存成记录时保留它。运行后状态写“正在做／Now”，按钮为 Pause、Stop；暂停后写“已暂停／Paused”，按钮为 Resume、Stop；第一张写“下一步／Up next”。Stop 保存计时但不完成任务：满一分钟的一段按整分钟存为一条记录；番茄钟到时由页面发出 Finish，最多记到目标时长；正计时最多记 4 小时，页面的计时也停在 4 小时。全局计时条（标题、时钟、暂停／继续、结束和完成，最后是“小窗计时”，见下）不变，正计时时它的时钟向上数；它按计划内容列居中，侧栏收起或调宽后仍居中。完成是一次 Tasks 写入：同一批里把这一天队列中的步骤标为已完成，与这个任务或其后代有关的进行中或暂停的计时按它自己的那天存为记录并停止。

**用时记录**（`src/FocusEntries.tsx`）：点“已用”在卡片内容列的左缘、这一行下方打开一个浮层（`position: absolute`，宽 300px、最宽为窗口减 32px，最高 320px、自己滚动，圆角 7，二级阴影），卡片和列表不移动。窄屏上右边放不下时，它在绘制前向左移，始终留在窗口内，页面不横向滚动。它不是模态的：打开时焦点进入浮层，Tab 可以在里面移动，也可以移出；焦点离开、点击外面或 Esc 关闭它，用关闭按钮或 Esc 关闭时焦点回到“已用”。标题是“用时记录 · Draft API”（13px 半粗）和关闭 ✕。每条记录一行：计时那一段的开始时间（账户时区，`HH:mm`），手动添加的写“—”，所以不另写来源；56px 的整分钟输入框（1–1440，名为“分钟，09:40”或“分钟，手动”）；删除按钮“删除记录”。下方是“合计 40m”和“+ 添加时间”，后者打开一行“[15] 分钟 [添加]”，默认 15，回车添加。输入框回车或离开时若有改动就保存，0 不接受（删掉时间用删除）；Esc 先恢复输入框，再按一次关闭浮层。删除立即执行，不再确认，需要时可以再加回来。写入都经过 App 的同一个写入队列，先确认再显示：这一行显示等待标记（`pendingEntry(id)`），确认的记录直接合并，不重新读取；失败时用 App 的错误条，输入框回到已保存的值。读屏会听到“已保存”或“已删除”。手动添加时间的领域：Plan 列出这个任务时用它的领域；否则用它最近一条记录的领域；再否则用 Plan 列出的父任务（`FocusTask.parent_id`）的领域；都没有则为空。浮层带 `data-no-drag`，在里面按下移动不会拖动卡片。没有记录时写“还没有记录。”。

**其他日期**：同样的列表，只读：没有开始、完成、拖动和计时方式，“调整计划”保留。今天和过去的日子仍可以打开记录浮层，修改或添加时间；将来的日子没有可记的时间，卡片下方只写估时。这一天没有步骤时写“这一天没有安排步骤。”。“已完成”勾选同样适用。

**其他用时**：记录留在记下它的那一天，步骤之后离开这一天的队列（在 Week 里移到别的日子，或移出日期）时，这一天的“已用”仍算它。今天和过去的日子在队列（勾选时还有“已完成”）下方另起一条同样的分隔标签“其他用时”／`Other time`，列出这些步骤，只读，内容 0.72 不透明，没有删除线，标题来自 Tasks 的 Focus 读取；它们的“已用”同样打开记录浮层。所以摘要的已用等于各卡之和，每条记录都能修改。

**已完成**（2026-10-19 owner 决定）：标题栏刷新按钮前有一个小勾选框“已完成”／`Completed`，样式同任务列表的那个（11px，muted），只在“日”出现，一直显示，每次进入 Focus 都不勾选，也不记住。勾选后，未完成的队列下方是一条 12px muted 的分隔标签“已完成”，再是这一天队列里已完成的步骤，按队列顺序，在它们自己的列表里，不在可排序的队列中。它们有同样的领域色条，内容 0.72 不透明，标题 muted 加删除线；勾选框是填满强调色的圆加勾，只是图示（“已完成”）；下方仍是“预计 30m · 已用 35m”，今天和过去的日子可以打开记录。没有开始，没有拖动；标题打开 Tasks 自己的任务对话框，在那里可以重新打开它（规划面板需要未完成的任务）。标题和估时来自 Tasks 的 Focus 读取（`FocusState.tasks`、`readFocus` 的 `tasks`），不会显示“任务暂不可用”。原来的“今天已完成 N 项”一行已经去掉。

**周**（`src/FocusWeek.tsx`）：先是一行数字，每项是 12px muted 的标签在上、18px 半粗的值在下：已用合计；工作、生活（带领域圆点；未分类只在大于零时出现，没有圆点）；完成步骤；预计用时比（“用时为预计的 112%”，只算有估时又有记录的已完成步骤，至少有一个时才显示；循环步骤这周完成几次就算几次估时；值写百分比，悬停显示整句）。然后是 7 列柱状图，图高 140px：每列是一个按钮，柱子按领域堆叠（工作在下，再是生活，未分类为 muted，顶部 3px 圆角），按这周最忙的一天缩放，上方写合计（窄时换成两行），下方星期在上、日期在下，总是两行，各列的标签在同一基线；名称如“10月13日周二：已用 3h 20m，工作 2h，生活 1h 20m，完成 3/5”，点击在“日”里打开那一天；今天的日期用选中色。最后是“时间去向”：最多 6 行，记录按任务的直接父任务（`FocusTask.parent_id`，标题是 `parent_title`）分组，没有父任务的任务自成一组；父任务通常是事项，但不一定。每行是这组最近一条记录的领域圆点、一行标题（截断时悬停显示全文）、按最大一组缩放的 4px 条和时长（时长列固定 56px，所以各行的条起止对齐），多出的组写“其余 N 项”。这周没有记录时写“这周还没有记录用时。”，柱子仍以零高度画出，形状不跳动。

**月**（`src/FocusMonth.tsx`）：同样的一行数字，只算这个月里的日子。下面是周一开头、5–6 行的 7 列日历，上方是星期；格子高 64px、圆角 5，左上是日期，下方是已用时间。底色是中性的墨色梯度，按当天分钟分四级：没有记录是 `--plus-surface`，一小时以内、三小时以内和更多依次是正文色 6%、14%、26% 混入背景；文字始终是正文色。领域色只用于“时间去向”的圆点和条，强调绿色只用于选中。不属于这个月的日子 0.45 不透明，只写日期，不是按钮，什么都不计。每个格子是一个按钮，名称同周的柱子，打开那一天。“时间去向”只算这个月里的日子。这个月没有记录时写“这个月还没有记录用时。”。

**读取**：今天的“日”就是页面自己的数据。别的日期、周和月用 `readFocus` 读取（一个月拆成最多七天一次，同时发出），Focus 打开期间按范围保存在组件里；每次写入确认后（App 的写入计数加一），正在显示的范围重新读取，结束的计时、完成和别处的改动都会出现；记录的写入还会立即合并进所有保存的范围。读取下一个范围时，上一个显示的内容留在原处，变淡（0.6）、不可操作并带 `aria-busy`；第一次读取时显示一行 muted 的“正在读取…”。读取失败时显示内联错误“读取失败。”和“刷新”按钮。统计在浏览器里由纯函数计算（`src/focus-stats.ts` 的 `dayTotals`、`weekStats`、`monthStats`、`groups`），不在服务端汇总。

旧日期的活动计时不冒充今天同名 ID 的活动计时，也不允许今天另启一段覆盖它。全局计时条在 Plan／Focus 切换时保留，不新增浏览器本地计时存储。

**小窗计时**（2026-10-20 owner 决定，“极致优雅美观，市场上的太俗”；外观由单独的设计阶段定稿，按它逐像素实现）：计时条最后一个安静的图标按钮“小窗计时”／`Mini timer`（lucide `PictureInPicture2` 17px，平时 muted，悬停同其他图标，窗口打开时 `aria-pressed="true"` 并变为强调色；再按一次关闭）。只在浏览器有 Document Picture-in-Picture（Chrome 116+）时出现；请求被拒绝时什么也不发生。点击时请求 320 × 120 的窗口，之后 Chrome 沿用 owner 拖到的大小和位置；版式从 240 × 72 到很大的窗口都成立。窗口里只有一份样式（`src/mini-timer.css`，以文本导入），以及从页面 `.plus-root` 复制的九个计算后的 `--plus-*` 颜色和字体，所以宿主的覆盖同样生效，不复制应用的样式表；没有深色模式。

内容（`src/MiniTimer.tsx`，DOM 与样式表一一对应）：白底，没有卡片、边框、阴影。所属事项（与步骤不同时，只在大窗口出现）、步骤标题（一行省略号，高窗口两行；不知道是哪一步时写 muted 的“专注”／`Focus`）、唯一的大字时间（`mm:ss`，满一小时 `h:mm:ss`，等宽数字，细体；番茄钟显示剩余时间），时间右边平时是“已暂停”，悬停或键盘焦点时换成暂停／继续、结束和完成（Plan 列出这个任务时才有完成）三个细线图标；最下面一条 1px 细线：正计时是这一步在会话那天的记录加本段时间对估时（按领域色填充，未分类用 muted；到 90% 时标签写“剩 4m”，超过后整条变警示色，填充停在估时处，写“超 7m”，都向上取整；没有估时只有空线），番茄钟是已过时间对时长，标签为时长。暂停时时间、填充和标签变淡。写入期间所有按钮停用并带 `aria-busy`；写入失败时细线的位置换成一行“没有保存。请回到主窗口查看。”／`Not saved. Check the main window.`（完整错误留在主窗口），下一次写入清除它。时间是 `role="timer"`，不朗读。动效都很轻，`prefers-reduced-motion` 时全部关闭。

三个按钮调用计时条自己的函数（`commandTimer`、`complete`），经过同一个写入队列，没有第二套计时状态，也不在浏览器里保存任何东西。时钟用小窗自己的定时器，在会话的下一个整秒刷新：主窗口隐藏或最小化时它的定时器会变慢，而那正是看小窗的时候。60 秒一次的计时读取在只有小窗可见时也照常进行，小窗获得焦点时也读取一次。会话结束（结束、番茄钟到时、完成被确认，或读取显示没有计时）、owner 关掉它、Plan／Focus 卸载时，窗口立即关闭，按钮回到未按下。

**后台模式**：会话存在时，宿主让 Plan／Focus 在其他页面后面保持挂载（`onSession` 报告会话的有无，`background` 表示宿主在显示别的页面），所以去 Today、Mail 或项目时小窗留着、按钮照常工作。后台时 App 只渲染小窗（React 树中位置不变，不会重新挂载），以及离开的问题等待回答时的计时条；保留数据、写入队列、计时读取、番茄钟的结束和离开时暂停；完整读取（别处的任务写入、回到窗口）等到 Plan／Focus 再显示：若有错过的读取就读一次，并在读完前停用写入，否则数据超过一分钟才读。没有会话时什么都不挂载；有会话时代价是窗口可见时每分钟一次 GetFocusTimer。后台的失败在别的页面上什么也不显示，打开 Plan 或 Focus 时重置。

**离开时暂停**（2026-10-20 owner 决定）：Focus › 日（今天）的计时方式后面一个安静的勾选框“离开时暂停”／`Pause when away`，样式同页头的“已完成”，悬停说明“正计时在锁屏或 10 分钟无操作时暂停，回来时问你是否计入。”。只在浏览器有 Idle Detection API（Chrome 94+）且宿主保存这个设置（`idlePause`、`onIdlePause`）时出现。设置属于这台设备，Tasks 存在 localStorage 的 `tasks.idle-pause`（`on`，没有即关），不是计时状态。权限只在勾选的点击里请求（`IdleDetector.requestPermission()`）；被拒时保持未勾选，后面跟一行 muted 的“浏览器没有允许检测离开。”，直到下一次点击；取消勾选不需要权限。只有设置打开且权限为 granted 时显示勾选：权限被收回就显示未勾选，再点会重新请求。

只管正计时，番茄钟不变。离开的起点：锁屏时为锁屏那一刻；`t` 时报告 10 分钟无操作为 `t − 10 分钟`；主窗口每 15 秒一次心跳，任何事件距上次心跳满 10 分钟（机器睡眠或页面被冻结）为上次心跳；几种同时出现取最早的。开始观察时（以及回答后继续时）看到的状态只是基线：若是无操作或锁屏，要先看到一次有操作且未锁屏才会暂停（无头 Chromium 启动时报告无操作；从手机开始的会话不能因为 Mac 正闲着就被丢弃）。发现离开时立即在 Tasks 里暂停在离开的起点（CommandFocusTimer PAUSE 带 `effective_time`），别的窗口和设备都看到已暂停；若 owner 不再回到这个窗口，离开的时间就不计。

回来（有操作且未锁屏）时，计时条的状态行换成问题“离开了 N 分钟，要计入吗？”／`Away for N min — count it?`（正文色；N 为回来时刻减 Tasks 的 `pause_time`，四舍五入到分钟，至少 1），暂停／继续的位置换成“计入”／`Keep` 与“不计入”／`Discard` 两个文字按钮（13px、500、强调色，悬停出现下划线）；结束和完成仍可用，它们结束这段已暂停的会话，离开的时间不计。小窗里问题占步骤标题那一行，两个回答占控件的位置（见小窗的设计定稿）。计入：RESUME 带 `effective_time = pause_time`，就像从没暂停过；不计入：RESUME 不带时间，从现在继续。问题出现时以及回答确认后（“已计入离开的时间。”／`Away time counted.` 或“已从现在继续。”／`Resumed from now.`），App 一直存在的 `role="status"` 区域朗读一次。问题属于那一次暂停：计时在别处有任何改变（新的 etag）就收起；刷新或关闭窗口也收起（不在浏览器保存），计时保持暂停，继续即从现在算。问题等待时再次离开不发送任何东西，只把回来时刻移到最后一次回来。关掉设置时已做的暂停保留，问题立即出现。

判断是纯函数 `src/idle-pause.ts`（off、arming、watching、pausing、away、asking 六个阶段，每个事件带时间，测试用假时钟）；`src/useIdlePause.ts` 接到浏览器上：设置打开、权限 granted、这个窗口持有观察，且有正计时在跑或被它暂停时，运行一个 `IdleDetector`（`threshold: 600000` 和 `signal`），否则中止；心跳；Web Lock `tasks.idle-pause` 让两个 Tasks 窗口只有一个观察（排队等待，前一个窗口关闭后接手；没有 `navigator.locks` 时照常观察）。命令经过 App 的同一个写入队列，执行时才读最新确认的计时（写入确认时立即更新，不等 React 渲染，所以排在一次计时写入后面的暂停带着那次写入返回的 etag）。暂停失败时第一次照常显示错误；之后每次心跳用同一个起点安静重试（同一个 request ID，丢失的回答会被重放），直到会话不再是正计时；读到计时恰好暂停在这个起点，就是自己那次暂停。精确度：Chrome 何时报告无操作和锁屏由它决定，起点可能晚一点（算作工作）；睡眠的误差在一次心跳之内（隐藏窗口最多一分钟）；暂停与继续按整秒，与其他暂停一样；服务端把时间限制在合法范围内。

## 写入与读取

任务详情只为用户编辑过的规划范围、领域、截止日期和提前量保留局部草稿；其余字段随任务刷新。草稿对应字段在别处改变时，先提示“保留我的修改／使用最新值”，保存暂不可用；保留仅接受当前值作为新的比较基线，仍要再点保存。规划写入只提交改变的字段，截止日期写入沿用现有接口并保留最新未编辑提前量。估时与新增步骤沿用原流程。

2026-10-15 owner 批准：拖动先显示、按序保存，只对下列拖动与移出放宽“写入期间禁用写入控件”。

- Review 跨列拖动和列内排序、Week 承诺排序、Week 拖入日期、“下一步”排序、跨日移动和同日排序落下后，卡片立即显示在预期位置。只有这张卡等待：变暗、小转圈、不可拖动，移出按钮隐藏。其他卡片、切周和下一次拖动照常可用。
- 等待确认的卡片在可访问名称中带“正在更新…”；抓手用 `aria-disabled` 停用但保持可聚焦，键盘落下后焦点留在移动的卡片上。减少动态效果时小转圈停止，只保留变暗。
- 等待确认的 Review 卡仍带拖动前的 etag：它的详情在确认或撤回前只读，详情标题显示同一等待标记；结束后显示服务端保留的规划范围。本周目标与任务无关，拖动期间照常可编辑。
- “移出日期”不提前删除：卡片原位等待，Tasks 确认后才消失。
- 所有写入进入同一个先进先出队列，按操作顺序执行。每次加入、移出、同日排序或跨日移动是一次 MoveFocusStep，只改这一个步骤，不写回屏幕上可能过时的整条队列；其他标签页刚加入的步骤和排在前面的移出都会保留。插到某步骤之前而它已不在那天时，Tasks 拒绝（“This step has moved. Refresh and try again.”）。每天最多 20 个步骤。任务写入带 Plan 持有的 etag，不先读取：每次确认的任务写入（规划、依赖、排序、估时）都返回新的 etag；过时时 Tasks 拒绝，撤回后重新读取。确认后换成服务端返回的任务或队列（队列替换，那天的用时记录保留）。
- 队列、计时和用时记录的写入各保留一个请求 ID，直到确认；回答丢失后的同样重试按原请求重放，不会写两次。
- 任一写入失败时，排在其后的写入不再发送，所有等待确认的预期变化撤回；原有错误区域说明“更改未保存，已恢复”、实际失败和其后未发送的更改数，队列空闲后重新读取。等待确认的卡片不显示为已保存。
- 邮件归类的保存只写 Todofy，在对话框里等待和报错。
- Week 的“添加步骤”（下一步托盘的一格输入）也先确认，但不打断打字：回车后标题先作为等待卡显示，输入框清空并保持打开，读取列出新步骤后换成步骤卡；一次只保存一个。
- 完成、在任务详情添加小步骤、任务详情里的估时下拉框、提前开始、标为进行中（含看板卡片的“开始”）、详情中的规划保存、添加或移除依赖、本周目标、加入今天、计时以及周回顾中的移到本月、留到下周和完成回顾仍先确认，写入期间停用写入控件；本周目标和“沿用”只用 `aria-disabled` 标为不可用，保留焦点（见[本周目标](#本周目标)）。

读取不锁定看板，也不重复读取写入已返回的结果：

- 打开、刷新按钮、返回标签页（距上次完整读取至少 60 秒）和写入后需要的读取都在后台进行，只转动标题栏刷新图标。刷新按钮带 `plus-refresh` 类，宿主可以用 CSS 把它移进自己的窗口标题栏（Tasks 隐藏 Chrome 标题栏时），组件和行为不变。与写入重叠的读取作废，队列空闲后再读，旧读取不会覆盖较新的确认结果；两次读取重叠时，先发出的读取晚到也不覆盖后发出的结果。
- 规划写入（UpdateTask，含标为进行中、提前开始和依赖）返回的任务、UpdateWeeklyBet 返回的目标、确认后的日期队列和估时保存后的时长直接合并，不再读七天；目标别处改过时只重读一次 GetPlan。
- 完成任务后仍重新读取，不在本地删除：Tasks 完成循环任务时会推进到下一次。读取完成前该步骤等待，不能再次完成。
- 离开 Plan／Focus 时，上次确认的数据只留在当前页面内存中；返回时立即显示，再后台读取。它可能早于一次完成或跨过午夜，所以本次读取完成前不开放写入；这次读取失败时只显示错误，并丢弃这份内存数据。离开时显示本周的，返回后跟随服务端的当前周（含周一轮换）。
- 加入日期和跨日移动直接写 Tasks 的队列：队列里只能放 Tasks 中存在的未完成任务，不需要同步。估时就是 Tasks 的时长，由宿主写入（`updateEstimate`）。

### 整行拖动

2026-10-19 owner 决定：Plan 的卡片（Review 各列、Week 的承诺、下一步、快速事项和日历里的步骤）和 Focus 今天的步骤像任务列表的行一样按整行拖动，用同一套设置（`src/row-drag.ts`，与 Tasks 的 `TaskDrag.tsx` 相同）：在卡片任何地方按下，鼠标移动 6px 后开始拖动；触屏上按住 250ms 才开始，按下就滑动时页面照常滚动。所以单击和双击从不开始拖动。完成勾选框、“开始”和“移出日期”按下后再移动也不拖动，标了 `data-no-drag` 的部分同样不会；写入期间、等待确认或正在计时的卡不能拖。

- 可拖的行显示抓取光标，标题按钮沿用它；原卡变淡到 0.3，浮层保留阴影；插入线是任务列表的 2px 强调色线。排序落下后卡片滑到预期位置（dnd-kit 的 250ms，减少动态效果时没有）。
- 抓手仍在，给键盘拖动、读屏说明和落下后的焦点用。事项卡（Review 和 Week 的承诺）的 17px 抓手一直显示，在卡片左边 25px 的内边距里。下一步、快速事项和日历卡的 14px 抓手只在悬停这张卡或键盘焦点落在它上时出现，标题不移动；触屏没有悬停，不显示它们。只有抓手设 `touch-action: none`，手机上卡片的行仍可滚动。
- Focus 只有今天的“日”可以排序（`src/FocusView.tsx`，同一套 `planningSensors`）：未完成的步骤是一个可排序列表，落下后是那一天里的一次 MoveFocusStep，插到落点那一步之前（放到最后时没有），立即显示在新位置并等待确认；读屏说“第 N 项”，键盘落下后焦点留在它的抓手上。抓手是卡片左边内边距里 12px 的叠加按钮“移动步骤：标题”，同样只在悬停或键盘焦点时出现，按住它拖动也可以；不能用时（写入期间、正在计时）它平时仍隐藏，悬停时才变淡显示。拖动的浮层与这一行同宽，留在指针下。正在计时或等待写入的卡不能拖；别的日子和“已完成”列表不在可排序列表里，记录浮层里按下也不会拖动。
- 没有引入任务列表的 `TaskDragProvider` 和它等待写入的 `suspend()`：Plan 和 Focus 仍用自己的写入队列和预期显示，慢的写入不会挡住下一次拖动。
