# 怎样判断简报是否更好读

自动测试检查接口、数据和故障处理；内容评测回答另一个问题：选出来的东西是否值得读，读完是否真正理解了它。这份说明用于人工评审和本地提示词对比，不是新的发信拦截规则。

## 先看读者能得到什么

不点链接读完一篇后，读者应该能说清：**原来有什么问题，这次发生了什么变化，为什么值得关注**。

- 先交代背景，再解释变化。不要用缩写、公式和一串数字代替说明。
- 分清“题目重要”和“这篇文章有贡献”。评测可靠性很重要，不代表每篇讨论它的论文都值得深读。
- 作者、机构、会议和期刊有助于判断信源，但不是结论正确的保证。应看具体增量、比较对象和实际证据；只读了摘要就如实说明。
- 链接是进一步阅读的选择，不是理解正文的前提。少量数字应能帮助比较，图表脱离正文也应讲得清楚。
- 留意兴趣之外真正重要的变化。某个领域没有好候选时，先判断是搜集不足，还是筛选失误，不靠配额凑齐栏目。

当前配置以新闻为主，默认最多 6 个公共话题、1 个研究类话题、1 个深读。评审时看产业、医疗、经济制度、世界局势和技术可用性是否有值得解释的变化，而不只是数论文少了几篇。高价值研究仍可成为头条，也不必每天宣布一个“改变世界”的突破。

## 固定标准，再做比较

每项按 0–4 分打分：0 表示明显缺失，2 表示基本具备但仍模糊，4 表示清楚且有证据支持；允许 1 和 3 分。每个分数附一小段原文和具体理由。以下权重用于比较，不自动控制生产流程。

| 选题维度 | 权重 | 主要看什么 |
| --- | --- | --- |
| 重要性与实质进展 | 25% | 是否改变了能力、成本、约束或现实处境 |
| 理解上的收获 | 20% | 是否值得花时间弄懂，而非重复熟悉的口号 |
| 证据与新颖性 | 20% | 是否分清已有结论、新证据和关键未知 |
| 整期取舍 | 20% | 是否避免同质话题挤占版面，保留重要的跨领域内容 |
| 调查可行性 | 15% | 问题能否在现有预算内得到有价值的回答 |

| 写作维度 | 权重 | 主要看什么 |
| --- | --- | --- |
| 解释是否清楚 | 30% | 非本领域读者能否理解问题、方法和变化 |
| 是否忠于证据 | 25% | 数字、归属和结论边界是否与来源一致 |
| 是否带来新理解 | 20% | 是否讲出了具体机制或有意义的未知 |
| 阅读体验 | 15% | 是否自足、简洁，背景和重点是否先讲清楚 |
| 时间关系 | 10% | 是否分清事件、发布、修订和观察期 |

事实问题单独记录，不用高分抵消。尤其要检查编造来源、偷换分母、混用比较口径、把相关性写成因果、把作者意见写成机构决定。暂时无法核实不等于已经证伪；措辞偏好也不应被升级成事实错误。

## 运行本地提示词对比

工具仍是 [scripts/evaluate_prompts.py](../scripts/evaluate_prompts.py)。它读取你提供的测试集，不扫描某个提示词目录，也不修改生产配置。可先查看参数，这一步不调用模型：

```sh
uv run --locked --extra codex python scripts/evaluate_prompts.py --help
```

实际对比会使用模型额度，必须另行批准。测试集和输出放在仓库、云同步目录及登录目录之外的私有位置；输出目录必须尚不存在，但其父目录应已创建。`--codex-home` 则指向已完成登录的服务专用目录：

```sh
uv run --locked --extra codex python scripts/evaluate_prompts.py \
  --suite /private/path/suite.json \
  --output /private/path/new-comparison \
  --codex-home /private/path/isolated-login \
  --allow-model-calls
```

工具不加载 `.env`，不读写服务数据库，不连接 Notion 或邮件服务，也不部署更改。默认模型与当前生产默认一致，可用 `--model` 指定；同一组对比应保持模型、输入、输出结构和超时相同。

测试集的顶层是包含 `cases` 数组的 JSON 对象。每项需要 `id`、`kind`、`prompt`、`instructions`、`schema` 和 `validation`，可选 `allow_web`（默认 false）。`discovery` 必须设置 `allow_web: true` 才能执行所需的搜索和来源访问；其余两个阶段的固定输入对比保持 false。`schema` 必须与生产阶段兼容；各阶段的校验字段如下：

| kind | validation 字段 | 测什么 |
| --- | --- | --- |
| `discovery` | `direction`、`issue_date`、`seeds`、`history` | 真实搜索和打开来源后，能否找到有价值的线索 |
| `selection` | `candidate_ids`、`source_urls`、`max_tasks` | 给定同一候选池时如何取舍，不额外搜索 |
| `summary` | `story_id`、`packets`、`paragraph_limit` | 只凭已有证据能否写清正文，不测试图表或审校 |

准备真实公开材料时去掉个人事件、账号和其他私有信息。用于声称内容改进的材料不能由示例数据替代；合成数据只适合测试工具的执行边界。

建议按以下顺序做一次有界比较：

1. 先确定要改善的问题、调用预算和判断标准，再保存原始输入、提示词及版本。
2. 用相同材料比较旧版与候选版。写作对比不开放额外搜索，避免把搜集差异误当成写作提升。
3. 匿名、交换顺序阅读结果；选题还应测试候选顺序变化，防止只偏爱排在前面的内容。
4. 选好版本后，再用没有参与修改的材料验证。一天的两个候选池不等于跨日期验证。
5. 记录所有尝试，包括失败、平局和跳过项。样本少或结果不一致时，结论是“有希望，仍待观察”，不是质量已经得到保证。

输出目录会保存请求、原始及校验后的结果、版本、来源访问记录、耗时和用量。`summary.json` 中的 `valid` 仅表示结构校验通过，不表示事实和文笔合格。工具不自动重跑失败调用；认证、配置或额度错误会停止剩余调用，已有的有限来源纠正也会计入记录。

关注单位时间或每十万 token 获得了多少有效线索，而不只是总量。缓存输入属于输入的一部分，不能再次加总；缺少用量记录时应标为未知。实验用量与每日简报账本分开。

## 哪些检查仍由测试负责

`make check` 覆盖候选去重和数量限制、引用与材料 hash、旧快照恢复、局部失败时保留其他已审内容、图表与邮件格式、个人事件位置、用量和防重复发送。提示词对比工具本身的隔离与授权测试在 [test_prompt_evaluation.py](../tests/test_prompt_evaluation.py)。

[tests/fixtures/editorial/](../tests/fixtures/editorial/) 保存三份仍用于回归的提示词基准，不是待上线配置。历史试验报告和淘汰的候选版本可从 Git 历史查看，不再放在现行目录中。

内容对比结束后不自动部署或发邮件。真实来源访问、模型输出格式以及收件效果，分别按 [接入指南](live-acceptance.md) 和 [供应商兼容检查](provider-acceptance.md) 验证。
