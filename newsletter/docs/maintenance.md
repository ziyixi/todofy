# 停机维护、升级与回退

普通工作仍走4个业务 RPC：启动整期、查询整期、查询刊期、按冻结 hash 批准每日发送。
业务维护只在已安装本项目、持有服务私有配置的操作员环境中运行。另有仅使用既有
send 机器身份的[发布排空接口](deployment-drain.md)，不增加 owner UI 或业务权限。
应用不自动读取 `.env`，密钥不能写入命令行、聊天、Git 或输出。

## 只读检查与互斥

```sh
newsletter admin status
```

此命令以 SQLite `mode=ro` 读取 `NEWSLETTER_DATA_DIR/newsletter.sqlite3`，无需供应商
登录或 HTTP token。它返回 `busy` 与各类在途工作计数，不修改业务数据库、不初始化
Store、不恢复任务、也不取得服务目录锁；可以在服务运行时检查。SQLite 为一致读取
在线 WAL，可能创建或更新必要的 `-wal` / `-shm` 协调文件，因此不是“文件系统零写入”。
不能用 `immutable=1` 忽略 WAL，否则可能漏看正在进行的工作。

缺失或不兼容数据库失败退出。`busy=false` 只表示当前没有 active 工作，不等于没有
queued 排队任务；这些任务保留原状，维护 CLI 不执行它们。它也不证明未来没有新请求，
因此它不是安全发布信号。支持新协议的版本先持久 `begin`，再等待
`freeze` 核对活动与实际 submitting 账本；旧版本仍须暂停外部触发器并核对在途。

两个修改命令都要求完整服务配置、既有数据库及显式操作参数：

1. 暂停外部 cron/触发器，确认没有另一套旧 sender；等待已在途的模型、Notion写入和
   发送完成，用 `admin status` 检查。对未知结果先核对回执，不制造新尝试。
2. 停止 newsletter 服务，保留原 data/auth/config 目录，不换空数据库。修改命令使用
   与服务相同的非阻塞 `service.lock`；服务仍在运行（即使空闲）或其他维护进程占锁时
   直接拒绝。取得锁后再次检查在途记录；不会自动清除残留的 running/submitting。
3. 备份后执行唯一获准操作。没有 `--force`，不启动 worker、定时器或全局 recovery，
   也不替其他任务做状态迁移。配置、锁或状态错误只输出安全失败代码。
4. 检查返回的运行/刊期回执，再恢复正常服务。重试命令创建的排队子任务只有服务恢复后
   才会执行。确认健康、冻结记录与调度后，再恢复外部触发器。

## 显式重启符合条件的逐题写作

仅在共享 writer 启动配置问题已修复、原运行符合受限恢复条件时执行：

```sh
newsletter admin retry-stories \
  --parent-run-id '<原运行UUID>' \
  --request-key '<本次操作的稳定幂等键>' \
  --issue-date '<原运行的YYYY-MM-DD>'
```

每个父运行最多创建一个新子运行，同键重复返回既有子运行，不能再次重启子运行。
不重跑发现、feed、选题或已确认的外部副作用；重新校验所有复用材料及其 hash，
再由正常服务执行新的写作/独立审校。原日期、模型、指令和政策继续冻结，原尝试不删除。
认证、额度、超时、取消/unknown、审校拒绝并不是这种重启的依据；详细资格见
[工作流说明](workflow.md#release-checks)。此命令本身不调用模型、不发送邮件。

## 另行批准的修订验证邮件

以下命令会实际调用已配置的邮件后端，必须由用户明确批准；它不是升级检查步骤。
不要用这个命令检查生产凭据；普通升级不包含测试邮件。

```sh
newsletter admin send-verification \
  --edition-id '<新的ready刊期UUID>' \
  --request-key '<本次批准的稳定幂等键>' \
  --expected-render-hash '<已核对的完整冻结hash>'
```

必须存在同日期已确认接受的普通每日投递，且目标是不同的 ready 刊期。验证投递使用
独立 `verification_sends` 账本，不改普通 `sends` 的每日唯一约束；默认每日期额外
至多一次验证尝试。发送仍绑定原数据库中的后端/发件人/收件人，Resend仍要求显式启用。
本机管理员使用服务私有配置与锁，不接收 HTTP Bearer token 或特殊审批 header。

同一天用户再次明确批准另一份新刊期时，在上面命令中额外提供：

```text
--after-verification '<最新已确认接受的验证刊期UUID>'
```

前序必须是同日期完整已接受链的最新末端，每个末端最多一个后继。旧UUID、失败或
unknown祖先都不能授权新投递。同一请求只返回持久回执，结果未知时不会再次调用供应商。
标准每日触发器不使用验证投递；一般的 `--send` 也不能携带该特殊授权。

## 安全升级与回退

- 先完成 `make check`、包/容器离线验收；不通过真实生成、Notion写入或测试邮件
  来代替部署检查。若另行执行需要模型额度的 schema smoke，必须获得相应授权。
- 记录当前镜像 digest、配置 revision/digest 与 pin 状态。目标服务、配置同步器和
  触发器使用同一已验收版本；不要只切换可变标签或顺带升级无关服务。
- 新版先按[排空合同](deployment-drain.md)关闭接单并取得 frozen 回执，暂停唯一
  触发器与配置同步器，再停服务；旧版使用原有暂停/核对方式。备份完整业务 data目录，
  包括存在的 SQLite WAL/SHM、冻结文件和所有投递/Notion回执；同时备份活动配置指针、
  releases、pin状态及私有环境配置。专用可刷新的登录缓存单独安全保存，不打印密钥。
- 更新镜像后保留既有 data/auth/config 挂载。新版本保持持久 gate，核对后同键
  resume，再恢复唯一调度。先检查启动健康与只读状态、已有冻结
  刊期/回执、配置同步状态，再恢复既有调度。不要在升级窗口临时创建另一个每日任务。
- 内容配置仍每900秒独立热更新，新运行冻结所选版本，旧运行和已发邮件不变。
  配置回退采用已有 pin/unpin，不回滚数据库，见[内容配置说明](content-config.md)。
- 生产 cron 保持 **07:00 America/Los_Angeles**（随夏令时），研究预算5400秒，
  外部等待7200秒，分别对应08:30与09:00，为09:30前到达目标留出余量。
  供应商故障和收件系统延迟仍可能影响实际到达；不要把目标写成无条件SLA。
- 回退代码必须能读取当前数据库结构、保留验证链和幂等检查。新版本已经发出任何
  新邮件后，不能恢复发送前的数据库备份；不能降级到无法表示验证后继的一日一行
  旧结构，也不能删账本“重试”。未知投递保留为未知，等待准确外部证据。

本地配置和上述步骤不证明线上已经部署或调度已恢复；每次发布单独记录实际镜像、
备份位置、检查结果和未验范围。历史验收结论不代表当前服务状态。
