# 内容配置，不重建镜像

内容现属于公开的 `ziyixi/todofy` monorepo。`main:newsletter/content-config/`
是可编辑源码，
`published:bundle.json` 是通过已测试引擎校验的发布产物，不另建配置仓库或 PyPI 包。
配置版本自动使用 monorepo Git commit SHA，无需手动增加版本号。旧部署同步器的
`ziyixi/newsletter` 来源不自动改变；后续须显式迁移唯一同步器，不能同时启用两套。

## 日常修改

1. 修改 `content-config/` 中需要调整的文件。
2. 提交并 push 到 `main`。CI 在候选镜像中校验配置；main 的 CI 成功后配置工作流才发布。
3. 等待配置工作流成功。同步器每900秒匿名读取 `published` 的一个固定 commit，
   下载整包并用当前部署引擎重新验证；通过后原子切换活动指针。
4. 下一次新触发采用新版本。正在运行的采集、汇编、渲染及重放使用原冻结快照；
   旧邮件、Notion 档案和发送账本都不会被重新生成或改写。

配置 CI 用实际 `Newsletter image publish` job 已成功的固定
`ghcr.io/ziyixi/todofy-newsletter:service-<monorepo commit>` 镜像进行离线检查，不调用模型、
Notion 或邮件。只有整体 CI 绿色或镜像 job 被跳过时，不把该提交认作已发布引擎。
代码兼容性以最近通过 CI 的主干为基准；Bazel 判定引擎不受影响时，继续使用此前已发布的镜像。
配置工作流只在 main 的 CI 成功后（或手动）运行，较早暂缓的更新也随之后的成功 CI 发布；不会把未发布镜像的提交当成引擎版本。
每个包都带有自己的 revision 及其摘要；除这两项外与 `published` 当前的包完全相同时（例如只改了代码的 main 提交），
不新建提交，服务继续使用原版本。读不到当前包时照常发布。
发布任务的仓库内置 `GITHUB_TOKEN` 只用于写入产物分支；服务器不持有此 token，
匿名拉取公开资源不需要 GitHub 密钥或 SSH 登录。

| 文件 | 可修改的内容 |
| --- | --- |
| `editorial.yaml` | 公共选题、研究主体、深读、研究候选数量上限 |
| `workflow.yaml` | 已注册节点、依赖和有界预算 |
| `discovery/*.md` | 现有八个搜集方向的题材要求 |
| `discovery/_sources/ai-ml.md` | AI/ML 公开信源入口，不是白名单或质量认证 |
| `researcher.yaml` | 研究员每期抓取的公开订阅源登记表（可选），见下文 |
| `prompts/discovery.md`、`prompts/selection.md` | 候选发现与全局取舍策略 |
| `policy/*.md` | 编辑要求、显式读者偏好；不依赖聊天 memory |
| `templates/edition.html.j2` | 受限邮件 HTML 模板 |

除上表规定路径外的文件不会发布。说明文档放 `docs/`，不要把 `.env`、token、
私有事件、服务器路径或登录缓存放入公开配置。安全规则、供应商权限、收件人、发信开关、
鉴权和模型运行环境不属于内容配置。新增节点类型、消息字段或引擎能力仍需更新代码／镜像。

## 新闻优先的默认预算

```yaml
max_public_items: 6
max_research_items: 1
max_deep: 1
max_research_candidates: 10
```

这些是上限，不是填满目标：最多6个公共话题，研究主体（含分类不明）最多1个，
全篇最多1个深读，30条候选池内研究／未知主体最多10条。
八个搜集方向不减少；论文仍进入材料库和近期候选索引，入选但未完成的调查会继续跟进，
但不自动获得刊出版面。
新闻应解释旧局面、发生了什么、谁受影响，不把一串新数字称为突破。
当前读者偏好让科技的实际变化更容易入选，同时保留重大国际新闻；这属于选题排序，
不是必须填满的栏目配额。独立世界新闻检索方向仍会运行，研究主体上限不变。
必知事件定义在 `discovery/03-world.md`，`prompts/selection.md` 逐字引用同一句，测试保证两处一致。
必知事件有两条互相独立的来路（控制台的必知追踪分别列出两者走到了哪一步）：世界方向把 change_basis 写成“必知：”开头并列出至少两家独立报道机构；
或者代码数出 3 家及以上头条源同报一个事件，以“头条共识：”开头的分类把它作为新闻候选放进候选池
（见下文），选题按同一定义独立判断它是否必知，家数多本身不算。符合定义的候选必须选入（通常每期至多
一项，最多两项），不受科技多数约束，排序和深读仍按解释价值，只读到元数据的不进深读位。
持续冲突中反复发生的袭击、伤亡更新、例行声明和例行政治攻防，没有规模、性质、参与方或政策回应的变化时
不入选。必知事件原文打不开时，世界方向最多再试两个替代来源，依次是同一事件其他头条源的报道、
官方页面、其他媒体，不在聚合站的转载页上耗尽尝试；仍读不到正文但已有多家独立报道时，
以“仅线索”范围如实交接，由采编阶段再搜索核对。选题不把未打开的头条线索并进已有新闻候选的任务，
否则代码会把该任务按研究计入或丢弃。
论文改成新闻标题或公司公告不会因此变成非研究；引用论文作新闻背景也不自动算研究。
规则能限制数量，不能保证模型的每次语义判断正确；真实质量需通过后续实际简报评估。

预算还必须满足 DAG 容量：公共话题不超过 selection.max_tasks，深读不超过 story_plan.max_deep，
研究候选不超过候选池容量。引擎当前支持公共话题1–8、研究0–话题数、深读0–2、
研究候选0–60；超范围在激活前拒绝，不到发信时才卡住。

## 研究员订阅源

`researcher.yaml` 登记约 55 个公开订阅源：arXiv 检索、Hugging Face Daily Papers、
AI 机构与作者博客、Nature/Science 及地球物理、地震学期刊，世界方向的综合新闻头条
（BBC、NPR、卫报、DW、半岛电视台、PBS NewsHour、France 24），经济方向的美联储、欧洲央行新闻稿和
BBC 商业、卫报经济、CNBC 头条，健康方向的 BBC 健康、KFF Health News、NPR 健康、FDA 与 EMA 新闻稿，
以及技术方向的 Ars Technica、TechCrunch、BleepingComputer、The Verge。
这些源加入时都以 HTTPS 直接返回 200、没有跳转；这不说明托管模型能打开它们的文章页。
nature.com 后来对不带 cookie 的订阅源请求时常以 303 跳到 cookie 检查，Nature 和 Nature Machine Intelligence
因此改由 Crossref 按 ISSN 读取：只留有摘要的论文，新闻和评论不再成为线索。
它取代原先代码里固定的三个元数据源，并从已退役的 Brief 移植而来；文件头写明 Brief 最后的提交，
未移植的条目（付费或仅作信号的源、站点地图、USGS 和停用条目）可从那里找回。开放的新闻头条源
最初也没有移植，世界方向因此没有任何线索、只靠几次临时搜索，2026-11-04 起恢复。
字段说明写在文件头；未知字段、YAML 锚点和标签会被拒绝，`direction` 必须是现有的
`discovery/<id>.md`，最多 80 个源，文件不超过 100 KB。

每期 07:00 运行时，`feeds` 节点读取随运行冻结的这份登记表，每个源抓一次：

- 只抓登记的 HTTPS 地址，不跟随跳转、不重试；同一主机串行并留间隔（arXiv、Crossref 3 秒，其他 1 秒），
  最多同时访问 4 个主机，源多的主机先抓，其次是头条源。每次请求 15 秒、按源限制字节数；
  节点在自身时限前 15 秒停止，保留已完成的源。
- arXiv 检索最近 4 天提交的论文，Crossref 取最近 7 天登记的期刊文章，参照源读取前一天的维基百科时事（见下文）；其余源默认只保留 7 天内且有日期的条目，
  新闻头条源设为 2 天。
  关键词、`requires_abstract` 和历史去重在本地完成，不调用模型。
- 同一作品来自多个源时按身份合并，`name` 不同才算独立来源。排序依次看独立来源数、Hugging Face 当天点赞分位、
  日期和登记顺序；每个方向轮流取各源，最多 20 条，交给对应方向的搜集模型。
- 标为 `role: headline` 的源（世界和经济方向的综合头条）在同一方向内合起来当作一份头版读：
  只取抓取时刻前 48 小时内、带时区发布时间的条目（没有时间的计入 `undated`），不再每源只取最新几条。
  代码用标题加描述首句做“组长式”聚类：条目从新到旧依次只和各组组长比较，
  词干（单数的前六个字母，所以 elected 和 elections、Ukraine 和 Ukrainian 算一个，Iran 和 Iranian 不算）
  按当天在该方向出现的条目比例计稀有度，至少共享 2 个稀有词、共享词的权重 log(条目数/出现数)
  合计不低于 8 才入组，否则自立一组；不做链式合并。通讯社式的模板标题（“某国无人机袭击某城，致 N 死”）
  共享大部分词，所以一方标题点名了另一方从未提到的罕见地名或人名（标题里不在句首的大写词，
  当天在该方向至多 3 条用过）时不入组，所以同一场战争里不同城市的空袭、两国各自的地震通常各成一组。
  当天用得更多的地名人名（如首都）不算罕见；只提同一位人物、没有别的专名的几条无关报道，
  以及模板化的伤亡通报，仍可能误并。
  描述只取条目自己的正文字段，Media RSS 的图片说明（如卫报的摄影署名）不算；以单词结尾的段落
  也算一句结束，所以卫报不带句号的导语不会和下一段连成一个首句。
  阈值用一天的真实头条离线校准，由合成测试钉住。
  只有 `name` 不同才算不同媒体（BBC 世界和 BBC 头条算一家）。
  已由普通订阅源或其他方向交出的那篇报道留在原处，只给报道同一事件的组加上它的媒体。
- 每组是一条线索：组长那篇报道的标题和地址，`source_basis` 列出组内全部媒体，附注的
  `independent_sources` 是家数、`headline_window_hours` 是窗口，`alternate_urls` 是最多 3 个其他媒体
  同一事件的报道地址，供主报道打不开时改开。方向内的组按家数优先、其次新近排序，
  头条源的 `max_seeds` 之和是该方向的组数上限，整组作为一个源参与轮流。聚类只用于排序和备用地址，
  不当事实：标题改写可能把一件事拆成几组，热门人物和地名也可能误并。
  大事件常被拆成好几组 3 家以上的组：某组反复出现的词（组内至少两篇用到）里，若有 2 个是当天
  该方向至少一成条目都用到的高频词、且排在它前面的某个 3 家以上的组也反复用到，附注写
  `headline_echo: 1`，表示多半是同一件事的另一组。
- history 只剔除命中的那条报道，同一事件其他媒体的报道照常成组。
- 线索只含元数据（已读范围“仅线索”），摘要和关注理由是固定说明；`venue` 是订阅源名称，
  `source_basis` 由代码写成“研究员订阅源：…（仅元数据，未打开原文）”。
  订阅源正文最多 300 字作为不可信摘录，只放在搜集提示的附注里，不进入候选、候选池或 Notion；
  Crossref 摘要只用于本地筛选，不作为摘录。唯一的例外是下文头条组的冻结摘要。

搜集模型自己决定打开哪条线索，打开后的候选按原有规则核验并写 `source_basis`；
未打开的线索只能作为仅线索候选，在搜集结果和候选池剩余的研究名额里出现。不增加模型调用、节点类型、
数据表或服务，`workflow.yaml` 中 `feeds` 的时限为 180 秒。

例外是头条共识：候选池节点读 `feeds` 产物的附注，3 家及以上媒体的头条组由代码分类为新闻，
basis 写“头条共识：BBC、NPR、DW共3家独立媒体48小时内的头条订阅源标题相近（代码按标题聚类计数，
可能把同一议题下的不同事件误并；仅元数据，正文未核对）”，每期至多 3 条：先取不带 `headline_echo`
的组、家数多的优先，同一大事件的其他组排在后面，所以大事件不会占满 3 个名额。它们排在其他线索前面，
因此一定进入候选池；其他媒体的报道地址放进候选的 `evidence_urls`（同样未打开，已读范围仍是“仅线索”）。
只有搜集阶段已把组内某篇报道（url 或 evidence_urls）作为 news 交接时才跳过这个组。
搜集候选是 unknown 或研究时共识照样进入，选题会把报道同一事件的候选合成一个任务；
搜集把这条线索原样交回时，代码改写它的分类并换上带备用地址的版本；
搜集打开过组长那篇报道却没有分类为新闻时，保留打开过的候选，只改分类，basis 不写“正文未核对”。
是否必知、是否刊出仍由选题判断。

进入线索的 2 家及以上头条组（必知事件可能只上了两家的头条），`feeds` 节点同时冻结组内每家媒体的
一条摘要：标题加订阅源导语（去掉图片署名，导语沿用 8000 字的清洗上限），连同媒体名、地址、
发布时间和这段文字的 sha256，写进产物的 `excerpts`。整份最多 64 KiB，家数多的组先冻结，
超出时其余的组整组不冻结，并记 `excerpts:trimmed:<n>`。
候选池节点只把池中候选（url 或 evidence_urls）指向的组传下去；选题任务的候选或 `source_urls`
指向某组时（最多 3 组），写作从代码生成的材料开始：每组一份，每家媒体一个已读范围为“摘要”的来源。
审校时，文字与 sha256 一致的冻结摘要在观察短讯（signal）里视同已读，不必再打开原文，
但审校仍须本轮搜索；这样的 signal 只有一段，写成“据X、Y报道”，所引的每一组都须有同组的两家媒体
（几组各引一家可能是不同事件），或另有本轮打开的原文；只凭摘要时，代码还逐个核对 signal 里的
阿拉伯数字都出现在所引摘要或其发布日期里。是否写明了媒体、有没有摘要以外的论断（以及用汉字写的
数字）仍由审校判断，代码不核对。正文、阅读卡和图表引用这些地址时仍须打开原文。
文字被改过、只有一家媒体，或写作自建的同地址材料，都不算冻结摘要；汇编时再按审校凭证里的
地址与 sha256 核对一次。所以采编打不开原文时，多家同报的大事至少能以一段注明出处的观察短讯刊出，
否则任务仍以延期或撤下结束，不会未经核实就发出。

任何源失败时 `feeds` 节点记为 `partial_failure`，其他源的线索照常使用；
节点产物的 `diagnostics` 逐源记录 `<id>:<code>`，代码只有 `ok`、`http_error`、`too_large`、
`parse_error`、`timeout`、`unavailable`、`unsafe_address`、`deadline`，另有 `truncated`、
`undated:<n>`、`invalid_items:<n>` 计数，以及 `registry:absent`、`registry:invalid`、`artifact:trimmed:<n>`、
`excerpts:trimmed:<n>`。
产物另有 `sources`，按源 ID（几个 arXiv 源同名，所以不用名称）记录代码、解析条目、通过筛选的条目、
分到的线索数和是否截断；合并的线索只计入最先产生它的源，头条组计入组长的源。
`headlines` 为每个有头条源的方向记录头条源数和抓取成功的头条源数（`feeds`、`feeds_ok`，少于前者时
共识少不等于当天平静）、头条窗口内的条目数、组数、3 家及以上的组数、最大家数和前 3 组的组长标题与家数，
都是公开元数据。两者和 `excerpts` 都不占线索的字节预算；没有节点读取前两者。
DW 和半岛电视台订阅源给每个链接加的 `maca`、`traffic_source` 参数与 `utm_` 参数一样去掉。
日志只有一行来源、成功、失败和线索数量。地址失效时直接改这份配置。

### 维基百科参照

`kind: current_events` 的源（登记表里至多一个，现为 `wikipedia-current-events`）不产生线索：它用 MediaWiki
parse API 读取刊期前一天（UTC）的维基百科 Portal:Current_events 页面（约 7KB）。07:00 运行时这一页通常只写了
七到九成，之后几天还会补写；事件按发生日归档，前一天公布的结果可能记在更早的一页。参照只保留冲突、政治与选举、
灾害、商业、健康、法律与犯罪（Law and crime）、国际关系（International relations）七类中带引用来源的条目，
至多 30 条，超过时各类轮流取（页面按类名字母排列，冲突多的一天不会挤掉政治），产物记为 `reference`。
必知定义里的终审裁决、重大制裁多归在后两类；科技、体育、文化等其余各类不核对。
页面有带来源的条目、却没有一行可识别的保留类名时记为 `parse_error`：标记改了形状，空列表会被读成“这天没有大事”；形状不认识的类名行不归入任何一类。
代码在抓取时比对每条事件和本期全部通过筛选的订阅条目：`feeds` 是不在历史里的条目中最好的匹配强度
（2 强、1 弱、0 无），`feed_title` 是那条的标题，`seeds` 是代表强匹配条目、且被交给搜集的线索（头条组的
成员由组长代表）；于是“订阅源里有、但路由截掉了”是 `feeds` 为 2 而 `seeds` 为空。`feed_urls` 是这些线索、
它们组里其他报道和强匹配条目的地址（至多 10 个），搜集在其中某个地址交接的中文标题候选也能认出来；
`previous` 是历史里已有的强匹配条目的标题，表示前几期已经见过这件事。匹配只看英文词和地址：引用同一 URL，
或共享至少 5 个词干、用不同的词点到条目里至少两个链接实体（地点、人物、机构）、并且共享一个不是实体名的
词（发生了什么），算强匹配；共享 3 个词干且点到一个实体只算弱匹配。用 11-01 到 11-03 的真实页面和当天订阅源
离线校准；同一冲突或选举里的另一件事仍可能强匹配，所以控制台总把匹配到的标题一起显示。抓取或解析失败只让
参照不可用，不把 `feeds` 节点记为 `partial_failure`，也不计入运行的订阅源失败数。
User-Agent 按维基媒体政策写明公开仓库地址。不用 In the news（更新太慢）或 mostread（噪声大）。

### 漏斗留痕

搜集产物另有 `observed`：`opened` 是这次调用尝试打开的最多 24 个公开 URL（排序），`opened_count` 是总数。
网关只记录打开动作，不记录页面是否读到，所以它们只是“尝试打开”。候选池产物另有 `dropped`：每个没进入
候选池的候选和订阅源线索各记一次 `{id, direction, reason}`，原因按最先发生的一步记为 `history`（历史里
已有）、`duplicate`（与已留下的候选重复）、`research_cap`（超出研究名额）或 `pool_cap`（超出候选池上限）；
与留下的候选同 ID 的副本不算丢弃。这些都是附加字段，旧产物没有，控制台对它们写“上线前未记录”；没有节点读取它们。
控制台另从候选池读出每个方向接续已刊线索的候选数（`threads`），以及每条头条共识的组带上了几家冻结摘要（`excerpts`）。

包内初始基线不含 `researcher.yaml`，离线 demo 和没有该文件的配置不抓取任何订阅源。
旧引擎不认识这个文件：配置若先于新镜像到达，同步器只记录错误并保留上一版，新镜像上线后自动恢复。

## 写作风格

`policy/editorial.md` 同时用于逐题写作和审校，`policy/reader-profile.md` 补充读者偏好。
默认按中文新闻讲清事件和背景，不给每篇例行附上反驳或免责声明。
影响结论的条件在正文就近说明；没有需要额外提醒的事项时，`limitations` 留空。
模板仍完整展示非空说明，但不再加醒目的“阅读边界”框，也不会按关键词删除模型输出。
这些调整不改变选题配比、篇幅预算或事实检查，不新增模型调用和发送门槛。

这里修改的是供服务同步的内容配置，包内初始基线和离线 demo 不随之改变。
离线测试能检查指令传递与渲染保真；模型是否真正讲得清楚，仍需看采用新配置后生成的简报。

## 模板与邮件兼容

模板使用有限 Jinja：if、for、set、非递归宏及少量已有过滤器。不允许 import/include、
任意函数调用、文件／网络访问、脚本、事件属性或 CSS 外部资源。只允许已冻结图表的 CID 图片，
引用链接仍遵循公开 HTTPS URL 规则。HTML源码最多64KiB，渲染输出最多1MiB；循环也有预算。
校验会离线渲染完整和可选栏目缺席两种输入，检查章节、图表解释、来源、阅读卡、私人事件和用量页脚没有丢失。
使用 email-safe 表格和内联样式；不依赖 JavaScript、远程字体或邮件客户端不一致支持的折叠组件。

模板热更新只用于绑定整期运行的邮件。纯渲染不再提供HTTP入口；本地
`rendering.render_edition()` 未提供冻结模板时仍使用包内模板，离线demo同样不会读取
生产活动配置。已有运行继续使用其冻结模板，活动配置损坏不能成为包内模板回退的理由。

## 离线检查

Linux Docker 主机运行 `bazel test //newsletter:container_test`：它只挂载声明的公开配置，
在声明的精确引擎镜像 ID 中构建并再次校验配置包，禁用网络，不调用模型或邮件。
`//newsletter:check` 已包含这个目标和合成配置回归；源码与镜像发布仍由各自 Actions 门禁处理。

## 部署、故障与回退

使用本仓库的 [VPS bootstrap bundle](../../tools/vps-bootstrap/README.md)。配置宿主目录由 uid10001拥有，挂给同步器可写，
挂给 newsletter 只读。同步器不挂数据库、业务 `.env` 或 Codex 登录，不暴露端口。
只运行配置同步循环，不创建第二个内容 cron；既有每日07:00洛杉矶调度保持不变。

首次启动必须显式 seed 一个通过验证的包内基线；没有活动配置时服务拒绝启动，
不会偷偷切换旧资源。已有活动版本时 seed 不覆盖。之后网络、限流、下载损坏、模板错误或
引擎不兼容只更新同步错误状态，保留最后可用版本。服务启动和每次新运行仍重新检查活动配置。

本仓库的 K3s 配置同步 Deployment 在启动前，用同一固定 digest 的 Newsletter 镜像
执行 `python -m newsletter.config_sync initialize`。它只在配置卷完全为空时 seed 包内基线；
已有活动配置只校验且不改写。非空目录缺少基线或基线损坏时失败，不自动重置配置。

配置维护使用已安装镜像中的 `python -m newsletter.config_sync`：`status` 只读，
`once` 拉取并校验一次，`pin <digest>` / `unpin` 是显式配置回退操作。生产执行仍需相应授权，
日常验收优先使用下文的 Fleet/Home 只读入口。

pin 会持久化并切换到已保存的版本，后续自动同步不会覆盖人工回退；unpin 后恢复自动追踪。
`status` 区分远端期望 commit、活动源 revision/digest、固定状态、最后成功时间和错误码。
`releases/<digest>/bundle.json` 保存历史不可变版本，`active.json` 只在完整落盘后原子替换。
配置目录纳入现有备份，但回退内容配置不需要也不允许回滚 SQLite 或发送台账。

## 只读监视合同

`GET /internal/monitoring/status` 继续使用 `version:2` 和独立的
`NEWSLETTER_MONITOR_TOKEN` Bearer 身份，响应为 `Cache-Control: no-store`。
editor、send 身份不能读取此接口，monitor 身份不能启动采编、发送或排空操作。

配置观察使用服务已挂载的只读 `NEWSLETTER_CONTENT_CONFIG_DIR`，调用与 CLI 相同的
`ConfigSync.status()`。响应的可选 `config_sync` 子对象只含以下九个字段，各字段允许 null：

| 字段 | 含义 |
| --- | --- |
| `active_revision`、`active_digest` | 当前通过引擎校验的活动配置身份 |
| `wanted_revision`、`wanted_digest`、`wanted_commit` | 同步器上次观察到的目标身份 |
| `pinned_digest` | 本地固定的配置 digest |
| `last_attempt`、`last_success` | 同步器最后尝试、成功的 Unix 秒，可含小数 |
| `error` | 有界的 `CONFIG_` 错误码，成功时为 null |

revision 为 40 位小写十六进制或 `packaged`，commit 为 40 位小写十六进制，
digest 为 64 位小写十六进制。目标是上次观察结果，不能据此证明它就是远端最新发布；
检查时间也不等于同步成功时间。没有配置目录时 `config_sync` 为 null。
本地配置状态无法读取或字段不合法时，子对象的身份和时间为 null，
`error` 为 `CONFIG_STATUS_UNAVAILABLE`，原有 `worker_healthy` 和业务计数照常返回。

监视读取不会拉取远端、切换版本、写配置、执行回退或重试。响应不含仓库、目录、配置包、
提示词、私有内容或异常原文；观察到配置失败也不表示业务 Worker 已不可用。

## 从 Fleet 与 Home 验收激活

Fleet 复用现有 owner 接口 `GET /api/v1/fleetStatus`，配置观察位于
`report.newsletter.config_sync`，界面的 Newsletter「内容配置」展示相同数据。
observer 将两项 Unix 秒转换为 `last_attempt_time`、`last_success_time`；
共享 wire profile 省略没有值的字段。身份来自配置卷，独立于镜像发布身份。

验收一次配置发布时，先确认主机报告为 fresh，再把活动 revision/digest 与公开
`published` 分支的 `bundle.json` 元数据比较，检查源检查时间是否晚于发布、是否有错误或 pin。
活动身份与 wanted 相同，只说明与上次检查目标一致，不能证明之后没有新发布。
配置轮询沿用 15 分钟、observer 沿用 5 分钟；Home 沿用现有状态缓存，读取页面不会触发配置激活。

Home 的 Newsletter 应用详情通过现有 Ops 响应显示配置状态、最近检查和成功时间，并链接到 Fleet。
配置检查失败或超过 30 分钟未检查会产生可关闭的应用提醒，保持进程健康与每日投递状态各自独立。
这些只读状态足以验收配置接管，无需进入容器读取状态文件。
