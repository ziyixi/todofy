# Notion 双库操作说明

Notion 用于浏览和整理，不承担采编或邮件发送的权威状态。SQLite 保存原始材料、研究结果、冻结刊期、发送幂等记录和独立同步回执；后台任务把这些已有内容投影到 Notion，不重新搜索、调用 LLM 或生成邮件。

## 两个数据库的职责

| 数据库 | 一行代表什么 | 页面正文 |
| --- | --- | --- |
| Newsletter 材料库 | 一篇具体论文／报告，或一个具体新闻事件 | 发现概述、关注理由、来源依据、相关公共研究记录和来源 |
| 每日简报档案 | 一个唯一 edition，而非仅一个日期 | 已冻结的简报正文、引用、原始 PNG 图表、选题记录、用量，以及明确授权的 Todofy 事件 |

同一天的日常版本、测试版本和修订版本可以共存，不能用日期覆盖旧刊期。关系列表示简报实际使用的材料，不等于所有被发现或被研究的候选都刊出了。材料元数据未知时留空，不通过作者名气、域名或 DOI 猜出机构、会议或论文质量。

材料以来源身份匹配，不靠标题相似度合并。发现和研究的正文版本保留为快照；最新可变元数据放在列中。档案正文与图表来自原有冻结刊期，不用当前模板重渲染旧邮件；发送状态等列可以更新，但不能改写已冻结的正文。Notion 不是邮件 HTML 的像素级复制品。

## 创建和授权

1. 在私人 Notion 页面下创建两个真正独立的数据库，不要创建同一个数据源的两个 linked view。
2. 为现有 Internal connection 开启 Read content、Insert content、Update content，并把两个数据库都授权给该 connection。关系字段要求目标数据库也可访问。
3. 复制各自的 **data source ID**。数据库／页面链接中的 ID 不一定是 data source ID，不要直接混用。
4. 新库保留默认标题列即可；其他受管列由初始化命令创建。已有同名列类型或关系目标不符会报错，不自动删除或转换用户字段。
5. 如果档案将包含私人事件，确认其所在页面、数据库和继承权限均仅对预期人员开放，不要开启 Publish 或公开共享链接。程序不能仅靠 API 读写成功证明所有 Notion 分享设置都是私密的。

凭据仅通过私有环境文件或服务管理器注入，不放入 Git、镜像、命令行参数、URL 或聊天。应用不会自动加载仓库中的旧 `.env`。已有 `NOTION_TOKEN` 可继续使用，不需要新增一套 token。

## 配置

在专用私有配置中设置以下项；这里的占位符不能原样使用：

```dotenv
NEWSLETTER_NOTION=notion
NEWSLETTER_WORKFLOW=dag
NOTION_MATERIALS_DATA_SOURCE_ID=<materials-data-source-id>
NOTION_EDITIONS_DATA_SOURCE_ID=<editions-data-source-id>
NEWSLETTER_NOTION_ARCHIVE_PRIVATE=false
```

`NOTION_TOKEN` 沿用私有环境中的值。双库 ID 必须同时配置、有效且不同；单独配置一个会拒绝启动。默认使用打包的 daily DAG；自定义 DAG 也必须支持 `publish` 尾部，不可切换回仍依赖旧 Notion 投影屏障的流程。

若用户已明确允许把私人事件保存在档案数据库中，再设置：

```dotenv
NEWSLETTER_NOTION_ARCHIVE_PRIVATE=true
```

这只影响每日简报档案，不会把 Todofy 内容放进材料库、公开采编上下文或公开搜索。未开启时，归档也不会绕过开关复制可能含有私人事件的邮件 HTML／纯文本。私人事件仍保持在公共内容之后。

已有 `NOTION_DATA_SOURCE_ID` 可以暂时保留：两新 ID 未设置时采用旧单库模式；两新 ID 都设置时使用双库，不再把新材料写入旧库。切换目的地或隐私设置不能通过删除本地同步账本绕过，应执行明确迁移；尤其不要删除投递账本。

## 初始化和迁移顺序

以下命令在已安全注入配置、安装了本项目的操作员环境或容器中执行。不要把密钥值追加为命令行参数。

1. 备份当前服务的 SQLite 数据，保留发送回执和冻结刊期；记录旧库与两个新库的准确目标。不要为 Notion 迁移清空 SQLite。
2. 先检查两个新库，不做远程写入：

   ```sh
   python -m newsletter.notion_cli setup
   ```

   它读取两个目标的字段，报告缺失项和冲突，不创建列、页面或邮件。

3. 核对无误后显式初始化缺失列：

   ```sh
   python -m newsletter.notion_cli setup --apply
   ```

   初始化先检查两个目标，再增补缺失的受管列；不会重命名标题列、删除已有列或重写正文。远程更新并非跨数据库原子事务，遇到中断先重新执行只读检查，确认现状后再处理剩余缺失列。

4. 使用完成 CI 验证的镜像和新配置启动服务。启动只检查现有 schema，不隐式运行初始化。授权错误、字段类型冲突或错误关系目标会拒绝启动；暂时网络故障会明确报告降级。
5. 后台任务自动读取本地历史材料和 ready 刊期并回填。不需要触发新的一期，不重新调用模型，也不为验证归档而发送测试邮件。迁移前的历史试运行标记为测试版本，保留真实原始内容和原有发送记录，不把测试标记理解为重新生成了 mock 新闻。
6. 查看只读状态；服务运行中也可执行：

   ```sh
   python -m newsletter.notion_cli status
   ```

   检查实体、正文版本、导入错误和同步错误；在 Notion 打开实际页面核对正文、图表、私人事件开关、来源与关系列。HTTP 成功或页面已创建不等于全部正文已同步。

7. 新库验证成功后，才按已确认的旧目标归档旧测试页面，优先移入 Notion 回收站以便恢复。不要误删数据库结构、未确认归属的页面，或使用“清库”操作重置本地邮件台账。清理 Notion 不授予重新发信的权限。

更换数据库、恢复旧备份或排查歧义写入时，应同时检查目的地绑定和同步回执。已有发送之后，不要恢复发送前的 SQLite 备份，否则可能丢失防止重复邮件所需的记录。

## 列定义

受管字段使用固定类型。标题列沿用数据库现有的唯一 title 属性，因此界面上可以仍叫 Name／名称。以下表格列出初始化使用的其他名称。隐藏技术列、调整列宽和创建视图不影响内容；不要删除或更改受管列类型。属性 ID 用于已建立的字段绑定，但不能据此假定随意重命名后重新部署仍无需检查；修改字段前先做 schema 检查，修改后再次验证。

### 两库共有

| 列 | Notion 类型 | 用途 |
| --- | --- | --- |
| 现有标题列 | Title | 材料标题或刊期与简报标题 |
| 同步键 | Text | 稳定业务身份，避免重试创建重复行 |
| 内容Hash | Text | 正文版本指纹，不是完整远程同步的单独证明 |
| 同步状态 | Select | 同步中／已同步；部分写入不会当作完成 |
| 测试数据 | Checkbox | 区分测试／模拟材料与正常使用数据 |

### 材料库

| 列 | Notion 类型 | 用途 |
| --- | --- | --- |
| 领域 | Select | AI/ML、科学、世界、经济、健康、技术 |
| 主题 | Multi-select | 可扩展主题分类；没有可信结构化标签时留空 |
| 材料类型 | Select | 论文、预印本、技术报告、新闻、数据、未分类 |
| 一句话价值 | Text | 已记录的具体贡献或关注理由 |
| 原始链接 | URL | 该材料的来源地址 |
| 发表日期 | Date | 来源记录的发表日期，未知则留空 |
| 首次发现 | Date | 本地最早发现日期 |
| 采编进度 | Select | 候选、已研究、继续跟进、已刊出 |
| 作者 | Text | 已提供的作者信息 |
| 机构 | Text | 已提供的作者机构 |
| 刊会／发布方 | Text | 期刊、会议或发布单位 |
| 发表状态 | Text | 来源明确说明的发表／预印本等状态 |
| 已读范围 | Select | 仅线索、摘要、全文；不等于已核实全部主张 |
| 采集方向 | Multi-select | 对应检索方向，区别于最终刊出栏目 |
| 来源版本 | Text | 已记录的来源版本 |
| 见于简报 | Relation | 指向档案数据库中实际采用该材料的版本 |

页面正文保留发现概述、具体贡献、关注时点、信源选择依据、来源链接及关联研究。一个研究记录可能综合多个来源，不据此把整份研究中的作者或结论误认为都属于这篇候选材料。

### 每日简报档案

| 列 | Notion 类型 | 用途 |
| --- | --- | --- |
| 刊期 | Date | 简报日期 |
| 版本类型 | Select | 日常、测试、修订 |
| 本期概览 | Text | 冻结导读，不另行调用模型总结 |
| 涉及领域 | Multi-select | 实际刊出栏目覆盖的领域 |
| 收录材料 | Relation | 指向材料库中的实际引用材料 |
| 发送状态 | Select | 未发送、发送中、已提交、已确认投递、失败、结果未知、模拟 |
| Token总量 | Number | 已记录的输入加输出总量 |
| 输入Token | Number | 输入用量，已包含缓存输入 |
| 缓存输入Token | Number | 输入的缓存子集，不重复计入总量 |
| 输出Token | Number | 输出用量 |
| 用量不完整 | Checkbox | 存在缺失的用量记录，不把缺失当零 |
| 包含私人事件 | Checkbox | 此归档是否包含获准写入的 Todofy 内容 |
| Edition ID | Text | 唯一冻结刊期身份 |
| Run ID | Text | 对应本地采编运行，旧记录可能为空 |
| 邮件Hash | Text | 原始冻结邮件 render hash，归档不更改它 |

`provider_accepted` 对应“已提交”，仅表示邮件供应商接受请求，**不是已进入收件箱**。当前发送台账没有最终投递证据时不会设置“已确认投递”；预留该选项不等于实现了新的邮件 webhook。Notion 同步成功也不能证明 Gmail 已收件。

## 同步、恢复与手工整理

后台同步任务与外部每日触发器是两回事：前者只搬运已有本地记录，后者才负责按日触发准备和获准的发送。无需为 Notion 新增 cron。暂时不可用时保留本地数据和错误码，之后继续独立同步，不降低正文质量门槛，也不阻塞邮件。

创建页面或追加正文的结果未知时，先按稳定同步键／已有正文读取核对，不盲目重复创建或追加。若远端无法确认是否已经落地，保持待核对状态；不要通过删除回执强迫重试。与既有状态冲突、重复同步键或被手工改动的正文需要操作员检查。诊断只输出安全错误码与计数，不输出 token、上游响应正文或私人事件内容。

历史本地刊期body即使包含JSON `null`、列表或其他非对象形状，也只留下该条记录的
安全导入错误，不应阻塞后续有效刊期；原始记录不被删改。后台失败日志只保留phase、
异常类型与哈希关联ID，不记录异常正文。取消/进程终止在持久化未知外部结果后继续抛出，
不会被当作普通成功或自动重试依据。升级与人工维护仍遵循[同锁维护说明](maintenance.md)。

正文冲突会按退避间隔重新做只读核对。只有远端正文重新匹配冻结快照后才恢复同步，例如用户撤销手工修改，或升级修复了 Notion 对链接的等价存储格式识别。已写入但未确认的正文先补记确认，不重新追加；真正的内容差异仍保留，不自动覆盖。链接比较仅兼容已验证的 query 参数值中 `:` 与 `%3A` 转义差异，不忽略其他参数、路径或正文变化，也不改写原始材料和内容 Hash。

不要直接修改程序生成的正文，手工笔记放在另一个页面并链接材料或刊期；Notion 修改不会反向影响下一封邮件或本地冻结内容。可在 Notion 界面自行增加以下视图，不需要改变采编代码：

- 材料库按领域分组；按发表日期排序；筛选继续跟进／已刊出。
- 档案按刊期倒序；单独筛选日常／测试／修订。
- 两库另建“同步待检查”视图，显示同步状态不为已同步的条目。

视图和列隐藏只影响浏览，不是权限隔离；包含私人事件的档案即使隐藏相关列，也必须维持数据库本身的私密授权。
