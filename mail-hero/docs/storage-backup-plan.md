# 邮件大小、容量、清理与备份方案

2026-09-26。用户已确认实施。下文保留设计依据；当前实现增加了storage-v1内容策略、分阶段清理、DO容量预留、持久告警和加密备份工具。生产启用与实际验收以docs/verification-native.md本次记录为准；历史邮件不自动纳入新期限。

## 实施前的现状快照

以下保留规划时的基线；已部署变化与未完成的生产验收以[验收记录](verification-native.md)末尾为准。

- 真实测试信 `Mail Hero Todofy test 20260926` 于 18:31:20.980 UTC 收到，6,957 bytes，解析 ready；18:31:25.195 第一次 webhook 返回 HTTP 204，投递成功。Todofy 18:31:29 进入 complete，返回任务 `6hf2W46X3Gc8hjV7`；通过 Todoist 的精确任务查询确认任务存在且主题匹配。
- 当前 Mail Hero 内容逻辑上限是 **5 GiB**，不是 Cloudflare 的计费硬上限；当前未启用自动保留清理。
- 原件最多 25 MiB。解析器把原始 `.eml`、解析 JSON、解码附件、冻结 webhook payload 分开保存。大附件会在原件与独立附件中重复占用空间。
- 目前 HTML/纯文本各有 2 MiB 解析预算；超限可能导致整封解析失败。webhook 正文上限另为 256 KiB，整个事件上限 1 MiB，解析成功不等于事件一定能创建。
- 保留清理当前只处理安全终态，每轮最多一封，积压时约十分钟继续；不能指望它马上清掉数千封历史邮件。
- 既有 self-host-on-vultr 使用 `offen/docker-volume-backup:v2.43.0` 备份主机挂载目录。实际调度、保留和加密来自私有 `env/backup.env`；本次未读取该文件，不能把官方默认值当成用户配置。目录被覆盖也不等于运行中的 SQLite 已获得一致快照。

代码依据：`cloudflare/src/native/{ingest,parser,pipeline,coordinator,api-settings}.ts`；现有主机备份入口为相邻 self-host-on-vultr 仓库的 `docker-compose.yml` backup 服务。

## 建议默认策略

目标是让 Mail Hero 作为可靠处理缓冲和短期收件箱；原邮箱继续保存完整邮件。不要让促销图片和附件长期撑大数据库，也不把未处理邮件静默丢弃。

| 对象 | 建议策略 | 用户可见结果 |
| --- | --- | --- |
| 整封原始邮件 | 保持平台 25 MiB 上限；不另设更低整封拒收门槛 | 平台超限可能拒绝，原邮箱副本仍在；Mail Hero 无法处理未到达 Worker 的邮件 |
| 单独附件 | 单个最多 2 MiB、每封合计最多 5 MiB；超出部分不保存解码副本，不上传消费者 | 展示文件名、类型、声明/实际大小及 `omitted_size_limit`；正文照常处理 |
| 内嵌装饰图片 | 默认不保存独立副本，不加载远程图片 | 图片占位及“未保存图片”提示，保留文字 |
| HTML | 移除脚本、样式及冗余标记；HTML 清理超过预算时使用有效纯文本，不能因装饰 HTML 超限丢掉可用正文 | 明示 `html_omitted`；无可用正文则进入 needs_review，不能伪造完整正文 |
| UI 纯文本 | 最多保存 1 MiB UTF-8 文本；结构/内存限制独立生效 | 明示截断及原始长度，不把错误解析当正常空信 |
| 消费者正文 | 最多 256 KiB UTF-8；超限按字符边界截断，增加结构化标记 | Todofy 能识别并在摘要/任务中显示“正文不完整”；不默默省略尾部 |
| 原始 `.eml` | 安全终态后保留 7 天 | 到期关闭原件下载；已提取正文及小附件仍可查看 |
| 解析正文、小附件、冻结 payload | 安全终态保留 30 天 | 到期清理内容，保留最小状态/去重记录 |
| 最小去重与交付记录 | 至少 90 天，建议 180 天 | 同事件仍可去重；事件过期后不承诺永久去重 |
| 待解析、失败、未接管事件 | 不进入自动内容清理 | 单独显示积压大小，提醒 owner 处理 |

这里的“安全终态”要求解析 ready，且满足：明确 archive；或者 forward 的冻结目标版本已经创建至少一条交付事件，并且全部交付均已被消费者持久接管。不能把尚未创建事件的空集合当成“全部成功”。两类均要求没有 policy_error、needs_review、未决交付或在途 claim。`delivered` 不代表 Todofy 后续业务完成，但 Todofy 已持久保存所需事件；需要原始附件的消费者必须采用更长策略。

**附件省空间分两步：**不写独立附件只减少重复；附件仍在 `.eml` 里。7 天原件清理后才会真正消除这部分主存储。备份里还可能保留至备份保留期结束，UI 和删除说明必须明确这一点。初版不在 SMTP 接收阶段重写 MIME 或边流入边删除附件，以免破坏持久接管和可恢复性。

超大原件的字节上限、MIME parts/嵌套/解码预算与 CPU/内存限制继续保留。丢弃附件不能消除解码时的全部内存开销，需验证 25 MiB、base64 和恶意嵌套夹具；不能仅加附件阈值便声称解决了内存问题。

## 合同与实现变化

1. 解析结果增加 `text_truncated`、`original_text_bytes`、`html_omitted`；附件增加 `storage_status`、`omitted_reason`，下载接口对已省略/过期内容返回明确状态。
2. 通用 webhook 为新增字段更新 JSON Schema 和合同。Todofy 先兼容这些字段，再开启生产截断。附件列表上限统一为 100，省略计数单独表达；计入 1 MiB JSON 总预算。
3. 同一事件冻结的 JSON bytes 和 event_id 永远不随新策略改变。只有之后的新事件使用新策略；不通过重建事件绕开去重。
4. 将现在的一次性“删除整封内容”拆为可恢复的原件过期、其余内容过期和账本清理。D1 保存各阶段完成标记；R2 删除成功后才减少对应物理待清理统计，崩溃后可以续做。原件到期后明确标记 raw_expired、禁用重解析；恢复扫描和重启不能把它当成丢件去复活，也不能阻断仍保留的正文下载。
5. 每封入站冻结内容策略版本。首次启用或缩短期限先展示会影响的历史邮件数量、容量和类型；历史内容不得随新默认静默清除。

## 容量：保留 5 GiB 起步，不直接顶满免费额度

R2 Standard 的 10 GB-month 免费量在账户层共享，现有 Vultr 备份也使用该账户；5 GiB 约为 5.37 GB，不能与 5 GB 混用。只有核实账户其他桶的用量和备份预算后，才能决定是否提高 Mail Hero 配额。

建议用 **定期清理 + 提前告警 + 明确超限行为**，而不是在 5 GiB 处随意丢旧信：

- 70%（3.5 GiB）：UI 容量提醒，列出原件、正文、附件、未完成事件的占用。
- 85%（4.25 GiB）：高优先级告警；推进已到期安全内容的有界清理，不缩短用户确认过的保留期。
- 95%（4.75 GiB）：紧急告警，预留接收及解析空间；不再写不必要的附件副本。
- 100%：按预留后的剩余空间决定能否接收；不能成功确认后再把新信扔掉，也不能删除失败事件腾空间。来源不一定重投，告警必须说明可能收信失败，并保留原邮箱副本。

实现时需将“尚未写入 D1 的原件”和“解析放大预算”计入 DO 原子预留，异常时回收预留；当前仅检查 D1 逻辑字节尚不足以做到严格容量控制。D1 不可用时保存原件的现有恢复路径也要受这个预留约束。

UI 分开显示：①逻辑内容；②待物理删除；③桶实际占用；④账户 R2 总量及查询时间。实际用量不可用时显示未知，不用本地账本冒充账单。保留每日配额 300 封/256 MiB，避免流量异常直接耗尽空间。

提高容量应是 owner 的显式操作。首选维持 5 GiB；若确实需要，按“账户剩余免费空间减去备份与恢复余量”调整，不能自动改成 10 GiB 或升级 Workers Paid。少量 R2 超额存储本身便宜，不能因此忽略操作费。

## 清理和告警如何运行

- 继续使用 DO Alarm，不增加邮箱轮询、Queues 或另一个数据库。
- 使用索引找最早到期内容；每次按 D1 查询数、CPU、对象数和删除字节共同限额。预算允许时推进小批次，不能固定无限循环。
- 测试目标覆盖 100 封/天稳态以及已有 3,000 封待清理的积压；先测每封实际查询成本，再定批量。当前约 144 封/天的清理上限需要优化，但不能突破 Free 每次调用的查询限制。
- R2 通用 lifecycle 不直接清理活跃 `raw/parsed/payload`，否则可能越过 D1 状态删除失败邮件。它只适合已隔离的暂存对象或由清单控制的备份前缀。
- 告警先落为 D1 去重的 alert 记录并显示 UI；外部推送采用一个 owner 配置的通用 webhook，如有现用自建通知服务则复用。只含计数、容量、错误码和管理链接，不含邮件正文。
- 相同阈值每天最多提醒一次，恢复后一次解除通知。外部通知失败保留待重试状态，不能把所有问题都只写到用户不常看的页面。
- 备份超过 36 小时无成功、未接管最老事件超过 1 小时、解析失败/拒收突增和容量 85% 以上均需提醒。阈值可按实测调整。

## 备份：复用现有服务器和工具，独立 Mail Hero 快照

不把 Cloudflare 备份任务塞进 Workers Free 的单次执行里，也不直接修改现有 Vultr 备份任务。新增一个隔离的 Mail Hero 收集目录及备份任务，复用当前服务器与 `offen/docker-volume-backup`。

每份完整快照包含：D1 SQL、其引用的 R2 对象字节和 customMetadata、原始对象 hash/大小清单、schema/代码版本、必要调度与入站预留信息、非秘密资源配置。`CREDENTIAL_KEY` 单独加密托管，恢复需要它；不能只备份 D1 或只同步桶。

建议每日一次，保留 **7 份每日 + 4 份每周**。完整包先在主机完成并校验，再公钥加密上传独立 R2 Standard 备份桶，同时保留主机本地加密副本。解密私钥保存在另一设备或密码管理器；每日备份时间与现有任务错开。暂存目录放在现有 `./data` 备份树之外，避免递归备份自身。

### 一致性是新增功能，不能省略

当前 MAINTENANCE_MODE 会停止新收件，且 D1 导出会短暂阻塞数据库请求。不能每天自动切到维护模式并声称邮件不受影响。

拟实现一个**有期限的备份租约**：

1. DO 建立快照编号、最迟结束时间与策略快照，暂停解析、交付和所有破坏性清理，等待已有工作到达可恢复边界；新邮件仍先登记 DO、保存 R2。
2. 备份窗口内收件采用冻结的已验证策略；策略变更接口暂时拒绝，不能因 D1 正在导出就把 forward 邮件误归 archive。DO 日配额和容量预留仍生效。
3. 固定收件序号边界，等待边界前已登记的原件写入完成或明确失败；将已持久保存但尚未进入 D1 的 raw 也纳入 DO 入站清单。再导出 D1 与必要 DO 控制状态。仅先后导出两个数据库不构成原子快照，需验证边界前所有登记都有确定结果。
4. 按 D1/DO 清单复制所有引用对象与元数据；活跃原件不覆盖、已引用对象不清理。首版明确让边界后的新收件归入下一次快照，manifest 标明覆盖序号和时间，不额外增加尾部日志备份功能。
5. 本地 hash、数量、必要引用验证完成后加密并上传，再核验远端对象、checksum 及完整 manifest；只有此时才标记成功、更新 last_backup_at 并轮换过期备份。上传失败保留上一份成功记录。租约失效禁止提交成功；超时自动恢复正常处理，未完成快照标为失败，不能自动清理恢复所需对象。

这是待实现、待 workerd 故障测试的设计，不把跨 D1/R2/DO 的原子事务当成已存在。先完成一次用户可控维护窗口的隔离恢复演练，再上线不会停收件的日常备份。备份凭据分别限制为源桶只读、独立备份桶读写以及必要 D1 导出能力，禁止使用它修改 Worker/Access；D1 导出所需的实际最小 API 权限需在实施时验证。

恢复到新的空 D1/桶，强制暂停发送；校验对象、schema 和密钥，重建 DO 任务，保留失败停止计数并保守恢复日配额。对于快照中的发送中/结果不确定事件，按原 event_id 向消费者对账，不能生成新 ID 自动重发。每季度演练；没有演练结果就不承诺 RPO/RTO。每日快照的目标 RPO 为 24 小时，原邮箱副本是补救来源，不代表自动恢复已实现。

备份保留和邮件删除不是一回事：内容从主桶删除后，备份最多还可保留约 4 周。用户主动删除的最小 ID 清单需追加同步到独立备份侧和本地主机，保留至少覆盖最旧快照；不能仅放在可能一同丢失的生产 D1 中。恢复必须先应用最新删除清单；拿不到时保持内容隔离，不能直接恢复可访问状态并声称不会复活。到期加密快照按独立前缀清理，绝不碰现有 Vultr 备份。

## 费用估算与实施顺序

以单份完整加密包 5 GB、最多 11 份估算，备份约 55 GB，存储标准价约 **$0.83/月**，尚未抵扣账户免费量；若每份 1 GB，约 **$0.17/月**。这是新备份存储的粗算，不是账户总账单或费用上限，现有备份、峰值、上传分片和操作数另计。

R2 Class A 跨过免费操作量后按百万单位计费，一档就可能超过 $2。因此限制扫描/重试/小文件上传次数比把存储卡死在某个整数更重要；使用有界 manifest 和每日归档，而不是频繁全桶扫描。Workers 保持 Free。

建议实施顺序：

1. 附件/HTML 降级和透明截断合同，先用合成大邮件验证，Todofy 先兼容。
2. 原件 7 天、其余内容 30 天的两阶段清理及原子容量预留；对历史数据预览后再启用。
3. 容量/失败/备份告警、逻辑与实际用量展示。
4. 一次完整隔离恢复演练，再实现并启用日常备份租约和独立归档任务。

上线验收至少包括：25 MiB 多附件、HTML-only 超限、有效 text 加巨大 HTML、正文 UTF-8 截断、100+ 附件、处理失败不误删、删原件后正文可读、满容量并发、删除中断恢复、备份与新收件/交付/删除竞态、备份恢复后稳定事件去重。全部通过前保持现有生产策略。

## 官方资料

实施调整：独立收集器使用服务器已有Python/GPG直接加密一致快照，不修改既有offen任务。服务器只需要专用备份API凭据，不保存Cloudflare管理员token、R2 S3 key、应用密钥明文或恢复私钥。操作及恢复边界见[备份说明](../deploy/backup/README.md)。

远端完整读回校验后提交HMAC receipt，轮转仅处理有verified标记的包。单包8GiB，已完成对象最多14个，归档与上传预留合计80GiB；超限停止新备份，不删除恢复材料。以上仍不是账户账单上限。控制清单与manifest限制50,000条/16MiB，超过明确失败。

当前账本至少保留180天，暂不自动删除去重记录。恢复工具只写新隔离目录；真实Cloudflare空资源导入、DO重建、未知交付对账及人工激活仍需单独验收。没有最新独立删除清单时保持隔离。
