# Cross-application contracts

This directory owns shared semantics, generated schemas, synthetic fixtures and dependency-free value rules.
IDL and codecs live in [proto](../proto/README.md); shared authentication lives in
[packages](../packages/edge-auth/README.md). Applications keep their own implementations and resources.

| Contract | Producer and consumer | Owner |
| --- | --- | --- |
| [mail.received.v1](mail-received-v1/mail-received-v1.md) | Mail Hero → its webhook consumer (Todofy) | Mail Hero |
| [ops-v1](ops-v1/README.md) | Application `Ops` entrypoints ↔ Home | Each application owns its answers |
| [platform-runtime-v1](platform-runtime-v1/README.md) | Platform daemon → release verifier and host observer | Platform |
| [fleet-report-v1](fleet-report-v1/README.md) | Host observer → Fleet | Fleet |
| [recall-archive-v1](recall-archive-v1/README.md) | Recall → archive stores and change-feed readers | Recall |
| [newsletter-ui-v1](newsletter-ui-v1/README.md) | Newsletter → console Worker → owner UI | Newsletter |

## Sources and changes

The IDL declares fields and value rules. The contract text adds acknowledgement, retry, retention and cross-field
semantics that a schema cannot express. Generate published schemas with `bazel run //proto:write_schemas`;
`bazel test //proto:check //contracts:check` checks generated bytes, shared contract types and both codecs.
Declare consumers in their Bazel dependencies. CI selects affected test leaves and release facades through the
native graph; there is no separate contract-to-application registry.

A contract change includes its IDL, generated schema, producer/consumer checks and intentional fixture changes.
Incompatible changes require the contract's versioning procedure. Inputs remain synthetic; no fixture contains
personal mail, tasks, browsing content or credentials.

## Frozen evidence

Current golden fixtures are exact producer bytes. Legacy schemas and `fixtures/legacy/` are frozen compatibility
evidence: do not regenerate, reformat or delete them. Each contract states its unknown-field and version rules.

- Mail Hero's fixture builder (`mail-hero/cloudflare/test/contract-fixtures.mjs`, `npm run contract:update` in that
  application) deliberately updates current mail fixtures. Review those changes with Todofy's consumer tests.
  Legacy fixture SHA-256 values are pinned on both sides. Every fixture has unique `event_id` and `message.id`;
  retries retain their original identity and bytes. Mail fixtures have no trailing newline, protected by
  `.gitattributes`.
- Ops fixtures pin strict/lenient codec behavior, closed enums, clock-dependent limits and generated/legacy Schema
  agreement. Producer and Home golden tests protect the bytes each side sends and stores. See the
  [adapter reference](ops-v1/IMPLEMENTATION.md) for query and deferral bounds.
- Recall fixtures protect record envelopes, unknown kinds, blob digests, tombstones and the complete archive layout.
  Its writer and workerd/smoke tests rebuild the archive using a loopback fake store.
- Newsletter fixtures are reader output from a synthetic SQLite world. Python and TypeScript round-trip the same
  answers; records omitted before instrumentation remain unknown, rather than becoming zero.

A schema or fixture check does not establish external business success. Mail's 2xx means durable consumer takeover;
provider acceptance, a verified release and an archived blob each retain their own documented meaning.
